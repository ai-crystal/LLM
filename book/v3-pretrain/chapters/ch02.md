## 数据从哪里来：Common Crawl 与开源语料

从 Common Crawl 的公开索引里挑一个 2024 年的快照，随手下一个 WARC 分段文件，一 GB 左右。`zcat` 解开，前几百字节是这样的：

```text
WARC/1.0
WARC-Type: warcinfo
WARC-Date: 2024-03-14T08:12:03Z
WARC-Filename: CC-MAIN-20240314081203-...
...
WARC/1.0
WARC-Type: response
WARC-Target-URI: https://example.com/news/2024/03/...
WARC-Date: 2024-03-14T09:41:27Z
Content-Type: application/http; msgtype=response

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 48210

<!DOCTYPE html><html lang="zh">...
```

一个文件里大约有两万条这样的记录，接着往下翻，会看到导航条、cookie 提示、广告位脚本、相关推荐列表、页脚版权声明，正文挤在中间。这就是这个行业最上游的原料：一份按月生成、谁都能下载、包含全世界公开网页的抓取归档。

从这堆字节到一份能训模型的语料，中间隔着几十道工序，体积缩到原来的百分之一上下。这一章沿着原料的流向走一遍：先看 Common Crawl 到底长什么样，再看四个有代表性的开源语料各自做了什么选择，最后把 token 数量摆在一张表上，看这些数字能不能互相比较。

### 一个月一次的快照

Common Crawl 是一个非营利组织，从 2008 年开始抓公开网页，早期几个月一次，近几年稳定在每月一次。每次抓取叫一个快照（snapshot），命名带日期，比如 `CC-MAIN-2024-10` 就是 2024 年第 10 次。单次快照抓二十亿到四十亿个页面，压缩后的原始响应在 200 到 400 TB 之间；十几年累计两百多次快照，总量在 PB 级。

每次快照会被切成三类文件，后缀说明它装了什么。

WARC 是原始存档（Web ARChive），一条记录对应一次 HTTP 交互，头部是 WARC 自己的元数据（目标 URL、抓取时间、长度），正文是服务器返回的字节，一行不删。HTML 原样在里面，包括内联脚本、注释、乱码。

WAT 是从 WARC 里提取出来的元数据，用 JSON 记录这一页的标题、语言猜测、外链、内链、HTTP 头。想统计“哪个站点被链接最多”，查 WAT，不用解 HTML。

WET 是纯文本，由 Common Crawl 自己那套抽取器生成，一页一段，页与页之间三个换行。它的体积只有 WARC 的十分之一上下，看上去最省事。

除了这三类文件，还有一份列式索引（columnar index），把每个抓到的 URL 记成一行：地址、状态码、内容类型、响应长度、抓取时间、语言猜测。这份索引有几百亿行、几十 TB，存成 Parquet，可以用 SQL 直接查。它的用处是让人在下大文件之前先做筛选——只取 `text/html`、状态码 200、长度大于 5 KB 的记录，能把下载量砍掉一大半。

抓取本身带有系统性偏差，这一点在使用前要清楚。热门站点每个快照都被抓几十次，深层的、很少被链接的页面可能一次也抓不到；`robots.txt` 禁止的目录完全没有；需要登录才能看的内容只有登录墙那一页。所以 Common Crawl 不是“互联网的副本”，它是“爬虫能到达的那部分互联网”，偏向英文、偏向被链接得多的老站点、偏向静态页面。按语言识别统计，英文占四成到五成，俄语、德语、日语各占几个百分点，中文在 5% 上下。

实际做一份语料，下载环节长这样：先拿索引表过滤出目标 URL（限定内容类型、状态码、最小长度、语言），把命中记录按所在 WARC 文件归并；由于一个 WARC 分段里通常只命中几十条，下载时要么整段拉下来（浪费带宽），要么对 gzip 文件发 HTTP range 请求、边解边丢（实现复杂得多）。这一步的工程细节很少有人写进论文，但它决定了“能不能在一个月内把整个快照跑完”。

还有一个统计上很重要的事实：不同快照之间 URL 高度重叠。同一批站点每个月都被抓一次，正文改动很小，模板几乎不变。96 个快照加起来看着是 15 万亿 token，去重之后剩下的独立内容远少于此。这也是后面去重一章要处理的主要矛盾。

### 为什么没人直接用 WET

WET 看起来最理想：纯文本、体积小、格式统一。真实情况是它的质量不够用。

Common Crawl 用的抽取器是十多年前的设计，目标是“把 HTML 标签去掉”，不是“把正文找出来”。结果经常是三种：正文和侧栏、评论、导航混在一起，段落顺序被打乱；整页只留下一句话，因为抽取器把主内容误判成了非正文；或者反过来，把页脚的版权声明重复了几十遍留在文件里。

更麻烦的是 WET 丢掉了结构。标题层级、列表、代码块、表格的行列关系，在纯文本里全部拉平。一个代码文件被抽成一段话，缩进没了，`def` 和函数体混在一行——这种样本对训练代码能力几乎没有价值，却会占掉 token 预算。

所以 2023 年之后的主流语料都不再用 WET，而是回到 WARC 重新抽取：FineWeb、Dolma、RefinedWeb 都是从原始 HTML 起步的。代价是算力。正文抽取器单核每秒处理二三十个页面，一百亿个页面就是三亿核秒，十万核小时量级；一个快照跑完，几千个核要转几天。这笔钱必须花，因为抽取质量决定了后面所有工序的上限——从一堆混杂文本里再怎么过滤，也筛不出一篇被丢掉的文章。

抽取器之间的差别也不小。同一批页面，分别用 trafilatura、Readability、jusText 跑，抽出的正文字数能差两三成，而差的那部分不是随机的：新闻报道三家都抽得好，论坛帖、问答页、带公式的论文、代码仓库的 README，各家差异很大。所以“用哪个抽取器”实际上是在选“哪一种体裁会被保留”，它比任何一条过滤规则的影响都大，却经常在技术报告里被一句“我们用 XX 做正文抽取”带过。

### C4：一份被规则裁过的网页

2019 年，Google 为训练 T5 造了 C4（Colossal Clean Crawled Corpus），它的做法是给整个行业定了一个廉价的基线。

原料是 2019 年 4 月的一次 Common Crawl 快照。清洗规则只有几条，全部可以在几个小时里跑完：

只保留以句末标点（句号、问号、感叹号、引号）结尾的行；整页里出现 `lorem ipsum`、`javascript`、`terms of use`、`privacy policy` 这类固定串就丢掉；正文只有一两句话的页面丢掉；命中一张脏词表就整页否决；最后把重复的三句片段去掉。

跑完剩下 750 GB 文本、一千五百六十亿 token。这个规模在 2019 年是足够大的，T5 用它训出了 110 亿参数的模型，效果不差。

C4 的代价写在那条“只保留句末标点结尾的行”上。凡是结尾不是句号的文本都不算数：代码、表格、诗歌、歌词、对话记录、公式推导，一律被切掉。结果是 C4 里的“网页”其实只剩新闻、博客和百科——句式完整、段落整齐的书面语。它干净、可复现、跑得快，但体裁极其单一。用它训出来的模型写论文摘要很像样，写代码和对话就明显弱。

这条规则的收益也很具体：它顺手删掉了导航栏、菜单、按钮文案，因为这些行几乎都不以句号结尾。一个粗暴的规则同时完成了“去噪”和“砍体裁”两件事，取舍就在这里。

### The Pile：22 个来源，825 GiB

2020 年，EleutherAI 造 The Pile 时的出发点跟 C4 相反：不问“怎么把网页洗干净”，问“一份语料要覆盖多少种文本，才能让模型见过足够多的体裁”。

答案是 22 个子集，合计 825 GiB。几个大的：Pile-CC 227 GiB（自己清洗的网页）、Books3 101 GiB（近二十万本电子书）、GitHub 95 GiB、PubMed Central 90 GiB（生物医学全文）、arXiv 56 GiB、FreeLaw 51 GiB（法院判决书）、StackExchange 32 GiB、USPTO 23 GiB（专利）、英文维基 6.4 GiB。

配比是手工定的，Pile 论文自己也承认这是拍脑袋。但它引入了一个后续被广泛借用的概念：有效大小（effective size）。直接按磁盘大小配比，会让书和百科这种小体量、高质量的来源几乎不起作用——维基只有 6.4 GiB，占 825 GiB 的 0.8%。所以小数据集在训练里被重复几个 epoch，按重复后的等效体积参与配比，维基的份额因此抬到百分之二上下，书和论文同理。

这个做法解决了一个真问题，也带来一个新问题：重复训练等于给这些文本加权，模型会把它们背得更牢。维基里的事实被记得特别准，原因就在这里；维基里的笔误和过时信息被学进去，原因也在这里。

Pile 还有两个选择值得记下来。它没有用“像维基就打高分”的分类器，正例只取 OpenWebText2（Reddit 高赞外链），因为拿整个 Pile 当正例会让分类器失去区分度。它对过滤的态度是保守的：宁可留下噪声，也不要因为规则太紧把某个体裁整个删掉——论文明确批评了那种“太像维基和太不像维基都删”的做法。

Pile 的影响超出了它自己的规模。2022 到 2023 年，大量开源模型（GPT-NeoX、GPT-J、早期的 LLaMA 复现）都用它或它的变体，它事实上成了“多样性优先”这条路线的基础设施。

它的问题也很具体。Pile-CC 的去重只用了十个哈希、Jaccard 阈值 0.5，粒度很粗，同一篇报道的转载基本没被删掉；Books3 里混着 OCR 错误明显的扫描件；GitHub 子集没有按许可证筛，法律风险留给了使用者。用 Pile 训出来的模型有一个可识别的毛病：它见过很多体裁，但每一种都不够深，代码能写但不长，论文能读但不精。原因不难找：825 GiB 分给 22 个来源，最大的网页子集也只占一成八，任何单一领域都喂不饱。

### 两份实验报告：Dolma 与 FineWeb

C4 的规则和 Pile 的配比都有一个共同问题：它们是结果，不是方法。别人拿到 750 GB 文本，不知道哪条规则起了作用，也不知道删掉的那部分里有什么。

2024 年的 Dolma 想改这件事。它交出的不只是数据，是整条流水线：三万亿 token、11.5 TB 文本，从约 200 TB 原始材料里筛出来，六个来源——网页（Dolma-CC，来自 Common Crawl）、代码（来自 GitHub 的宽松许可子集）、Reddit 讨论、学术论文（peS2o，四千万篇）、书（古登堡加其他公版书）、百科（维基、Wikibooks）。

Dolma 在工程上有一个设计值得单独说：标注与过滤分离。每个文档进来，先被一串标注器（tagger）打上属性——语言是什么、质量分类器给几分、有没有命中脏词表、是不是重复、属于哪个来源——属性写成结构化字段，和文本存在一起。过滤的时候不重跑流水线，只写一条查询：语言是英文、质量分大于 3、未标记重复、来源是网页。改阈值只需要重跑查询，几小时出结果；传统流水线改一个阈值要重跑几天。

这让“某条规则到底有没有用”第一次可以在同一个原料池上反复对照。Dolma 论文做了这样的对照：把 Gopher 式规则、C4 式规则、分类器过滤分别打开，看下游小模型的困惑度和基准分数。结论不算惊人但很有用——大部分规则在小模型上的收益在噪声范围内，真正稳定有正收益的是语言识别、去重和一套很粗的质量规则。

同一年，HuggingFace 的 FineWeb 把这件事推得更远：它把语料当成一篇实验报告来写。

规模是 15 万亿 token、约 40 TB，覆盖 2013 到 2024 年的 96 个 Common Crawl 快照。原料比 Dolma 更单一——只有网页，但时间跨度长得多，2013 年的页面和 2024 年的页面在 HTML 结构、广告密度、模板样式上差别很大，这本身就是一个压力测试。

FineWeb 最重要的产出不是那 15 万亿 token，是它公开的消融结果：五十多个候选过滤器，每一个都单独跑一遍小模型，看验证集损失和基准分数。结论跟直觉有出入——很多被广泛抄用的规则（比如“删除不含停用词的段落”“删除重复行超过 30% 的文档”）在它的实验里没有可测量的收益，有的还略微有害。真正有效的只有几条：语言识别、C4 那套句末标点规则、URL 黑名单、以及去重。

去重那一项还得出了一个反直觉的结论，后面讲去重时会展开：逐快照独立去重剩下的 20 万亿 token，效果明显好于全局去重剩下的 4 万亿。删得多不等于干净，删错了等于丢信息。

FineWeb 之上还有一层 FineWeb-Edu：用一个 Llama-3-70B 给 46 万个网页打“教育价值”0 到 5 分，再蒸馏成一个线性分类器，把 15 万亿 token 筛到 1.3 万亿。这 1.3 万亿训出来的模型，在一批知识类基准上打赢了用全部 15 万亿训的模型。这个结果后来被反复引用，它说明“token 数量”和“token 质量”不是同一根轴上的两个刻度，而是两根轴。

### 代码、数学、书、百科

网页之外的四类来源，各自有各自的供应链和各自的坑。

代码的主流来源是 GitHub。The Stack v1（2022）从公开仓库拉了 6.4 TB 原始文件，过滤后留 3 TB，覆盖三百多种编程语言。过滤规则看起来琐碎但每一条都有理由：只保留宽松许可证（MIT、Apache-2.0 等）的仓库，规避法律风险；删掉自动生成的文件（带 `DO NOT EDIT`、`Generated by` 头部的）、压缩过的单行文件（一行几万字符）、行太长或平均行长异常的文件；删掉几乎不含字母数字的文件；再做文件级精确去重和仓库级近似去重——同一个库的几十个 fork 会带来大量重复。

代码语料有两个别处没有的问题。一是污染：HumanEval、MBPP 这类评测题的答案就在 GitHub 上，不显式剔除，模型等于考前看过卷子。二是许可证：GPL 代码能不能进训练集，至今没有法律定论，多数团队的做法是只收宽松许可，代价是丢掉一部分高质量代码。

数学的来源最分散。网页上的数学以图片和 LaTeX 混排出现，纯文本抽取经常把公式抽成乱码。OpenWebMath（2023）的做法是从网页里挑“数学密度高”的页面——公式标记、数学词汇、LaTeX 环境的密度——再按质量分过滤，最后得到 147 亿 token。Proof-Pile-2 把 arXiv 论文、OpenWebMath 和代码里的数学库混在一起，550 亿 token。这个量级跟网页比很小，但在早期模型上带来的数学能力提升非常明显，说明这类数据“单位 token 的信息密度”远高于网页。

书是稀缺资源。Books3 收了近二十万本电子书、约 100 GiB，来源是影子图书馆，法律地位灰色，2023 年之后陆续从公开语料里被移除。古登堡计划的七万本公版书没有这个问题，但体裁偏老——十九世纪的句式和当代英语差别不小。书的 token 密度高、句子长、跨段连贯，是模型学习长程结构最有效的材料，所以各家都尽量留 3% 到 5% 的配额。

百科的量最小、作用最集中。英文维基 680 万条、约 40 亿 token，只占一份大语料的千分之几，但它是事实密度最高、格式最规整的来源。它在训练里通常被重复好几遍，原因前面说过：体量太小，不重复就学不进去。中文、日文、阿拉伯语这些语言的开源高质量语料更少，维基往往是小语种唯一像样的来源，这也解释了为什么多语言模型在小语种上的表现高度依赖维基。

### 中文语料：一条更窄的路

前面这些语料都以英文为中心，这个偏向不是巧合。Common Crawl 里中文只占 5% 上下，而这 5% 里质量最差的一档又格外多：站群、采集站、伪原创、机翻、SEO 垃圾页，正文常常是几百字的洗稿，配一堆关键词。英文网页里也有这些东西，但英文的基数大，好的那一部分足够撑起一份语料；中文的基数小，噪声一多，筛完就不剩多少。

公开的中文语料因此普遍比英文小一到两个数量级。悟道 2.0 开放了 200 GB 文本，CLUECorpus2020 约 100 GB，ChineseWebText 做到 1.4 TB，多语言语料 CulturaX 有 6.3 万亿 token 覆盖 167 种语言，中文在其中占一成上下。把这些加起来，去重、去噪之后能用的中文 token，量级在几千亿，而英文是十几万亿。这个差距直接决定了中文模型在很多任务上为什么“感觉差一点”。

中文还有一个分词层面的额外成本。早期模型的词表是按英文设计的，一个汉字常被切成两个甚至三个 token，一段一千字的文章要一千五到两千个 token；同样的内容用英文写，token 数只有三分之一。这带来两个后果：中文的训练成本按 token 计翻了一倍多，上下文窗口能装的中文内容只有英文的一半。2024 年之后国内模型普遍把词表扩到十二万到十五万，专门给常用汉字和中文词留位置，就是为了把这段损耗补回来——词表那一章会算这笔账。

去重在中中文上还有一个英文没有的难题。采集站的“伪原创”通过同义词替换、段落重排、加几句无关内容来绕过重复检测，字符级的 MinHash 对这种改写几乎失效：5-gram 集合的 Jaccard 可能只有 0.3，但两篇文章讲的是同一件事、来自同一个源。要处理它，得用语义相似度或者段落对齐，代价是算力高两个数量级。这也是中文语料规模上不去的隐性原因之一：同样的过滤预算，在中文上只能处理更少的数据。

### 一张 token 账

把上面这些数字摆在一起，能看出各家用的是同一批原料、不同的取舍。

|---|---|---|---|---|
| C4 | 2019 | 单次快照 | 750 GB | 1560 亿 |
| The Pile | 2020 | 22 个来源 | 825 GiB | 3000 亿 |
| RedPajama-1T | 2023 | CC + 六类 | — | 1.2 万亿 |

读这张表要带四个提醒。

第一个是分词器。表里的 token 数是用各家自己的分词器算的，C4 用 T5 的 SentencePiece，The Pile 用 GPT-2 的 BPE，FineWeb 用 GPT-2 的，Dolma 用 Llama-2 的。同一段英文，三万词表和五万词表算出来的 token 数能差两成，中文能差一倍。所以“15 万亿”和“3 万亿”放在一起比，误差比它们之间的差距小不了多少。

第二个是重复。token 数把重复算进去了：一个页面出现五次就是五倍的 token。Pile 的维基被训了两三个 epoch，FineWeb 逐快照去重后仍有跨快照重复，Dolma 的三万亿里有一部分是同一篇文档的不同版本。想要“不重复的 token 数”，得先做全局去重，而全局去重本身又会删掉有用的信息——这是后面一章的主题。

第三个是有效信息。C4 的 1560 亿 token 全部是通顺的书面语；Common Crawl 抽出来的 15 万亿里，可能有三分之一是模板页、导航文本、商品描述、机翻内容。按 4 字节每 token 的粗略换算，15 万亿 token 约 60 TB 文本，而 96 次快照的原始响应加起来在几十 PB 量级——从原始字节到进训练的 token，保留率在千分之几到百分之一之间。这个比例听着苛刻，其实合理：网页里八成的字节是标签、脚本和图片，正文抽出来又有一半是重复和模板。

第四个是不同来源不能相加。“15 万亿网页加 7500 亿代码，一共 16 万亿 token”这种说法没有意义：同样一个 token，代码里的平均信息量比网页高得多，一份代码文件被读一遍顶得上十篇营销稿。实践中的做法是按来源分别定配额，而不是把所有来源倒进一个大池子再按 token 平均。这也是为什么“总 token 数”作为一个指标越来越不可信，各家开始分开报“网页多少、代码多少、数学多少”。

留下来的这些文本里还有多少是正文，取决于下一步。Common Crawl 的页面里，正文字符占比常常不到一半，剩下的是导航、广告、推荐位、页脚——这些东西会被模型当成语言来学，而且因为它们在不同页面上完全一样，会被记得特别牢。下一章就进这道工序：怎么把正文从页面里剥出来，怎么判断这段文字是哪种语言，以及为什么每一条过滤规则都在拿召回换精度。
