## 一张账单：参数、显存、token 与价格

一个十二人的团队给一家电商做客服机器人，七月上线。上线前他们算过账：一天两万次对话，每次调用按一分钱算，一个月六千块，写进了预算表。

八月结账，两万三千块。

差了近四倍。团队第一反应是“供应商是不是涨价了”，查了报价单，没有。第二反应是“是不是有人在刷”，查了调用日志，也没有。真实的原因是两条缓慢的曲线。

第一条：平均输入从 800 个 token 涨到了 4000 个。上线时提示里只有一段客服话术，后来为了答得准，他们往里加了历史对话、用户订单摘要、知识库检索出来的五段文档、一份三百行的退换货政策。每加一样，都只是几百个 token，没人觉得是钱。

第二条：平均输出从 150 个 token 涨到了 400 个。因为模型换了新版本，回答变得更详细，他们还加了“请解释原因”的要求。

输入涨了五倍，输出涨了不到三倍，账单涨了四倍。这两条曲线乘在一起，就是那张账单。

这一章把这笔钱拆开。一个 700 亿参数的模型，服务一次请求，到底在花什么。

### 700 亿参数，落在显存里是多少

先说参数。700 亿，写作 70B，指的是模型里可调的数字有 700 亿个。这些数字在训练完成后就固定了，推理时只需要读，不需要改。

每个参数的精度决定它占多少空间。最常见的推理精度是 16 位浮点（fp16 或 bf16），每个参数 2 字节。700 亿乘 2 字节，是 1400 亿字节，也就是 140 GB。

这个数字决定了第一件事：一张 80 GB 的显卡装不下。至少要两张，而且两张 80 GB 一共 160 GB，装完权重只剩 20 GB，什么都干不了。

所以 70B 模型的常见部署是四张 80 GB 的卡，总显存 320 GB。140 GB 给权重，剩下的留给运行时的其他开销。

如果换成 4 位量化，每个参数 0.5 字节，权重降到 35 GB，一张 80 GB 的卡就能装下，还余 45 GB。这是量化最直接的收益：把“四张卡”变成“一张卡”，硬件成本降到四分之一。代价是精度损失，通常体现在长尾知识、复杂推理和格式稳定性上，简单的问答和抽取任务几乎看不出差别。

显存不止装权重。推理时还有两块开销。

一块叫 KV 缓存（KV cache）。模型生成每个 token 时，都要回头看前面所有的 token，为了避免重复计算，前面算过的东西会被缓存下来。这部分大小和上下文长度成正比，后面单独算。

另一块是临时工作区。每一层计算都要产生中间结果，这些结果用完就扔，但同时存在的量不小。上下文越长、并发越多，这块越大。

这三块加起来才是真实占用。很多人以为“70B 模型需要 140 GB 显存”，这只说对了三分之一。

顺带说一个对比：训练时的显存需求和推理完全不是一个量级。训练要存中间结果，还要存优化器状态。常见的 Adam 优化器每个参数要额外占 8 字节左右，70B 模型光是优化器状态就是 560 GB，加上权重和计算过程中的临时数据，一张卡根本放不下，必须把模型切开放到几十张卡上。推理只需要读，所以两张卡起步；训练要写，所以要一个集群。这也是为什么微调比推理贵得多，而全量预训练只有少数团队做得起。

### 每吐一个字，要搬多少数据

模型生成一个 token，要做多少次运算？

粗略的算法是：每个参数参与一次乘法和一次加法。70B 参数，就是 1400 亿次运算。这个数字听着大，但对 GPU 来说不算什么——一张 H100 每秒能做上千万亿次运算，1400 亿次只占它万分之几秒。

真正的瓶颈不在算，在搬。

生成是逐字进行的。要算下一个 token，必须把全部 140 GB 权重从显存里读一遍，跟当前的输入做运算。算完一个 token，这 140 GB 就作废了，下一个 token 要重新读一遍。权重没有变，但硬件不知道你还要用，它必须再搬一次。

搬运速度由显存带宽决定。一张 H100 的显存带宽是每秒 3.35 TB。140 GB 除以 3.35 TB 每秒，等于 42 毫秒。也就是说，单卡、不做任何并行的情况下，每生成一个 token 至少要 42 毫秒，一秒最多 24 个字。这是物理上限，跟模型多聪明、代码写得多好都没关系。

把权重切到 8 张卡上，每张卡只读自己的 17.5 GB，理论上 5.2 毫秒一个 token，一秒 190 个字。实际达不到，因为卡与卡之间要通信、要同步，实际能到 50 到 90 个字每秒，已经算不错。

这里有一个反直觉的结论：**大模型推理的瓶颈是显存带宽，不是算力。** 提高算力对生成速度帮助有限，提高带宽才有用。这也是为什么新一代加速卡拼命堆显存带宽，而不是只堆浮点性能。

这条判断有边界。它成立的前提是“一次只算一个 token”。批量变大之后，同一份权重一次要跟几十个输入做运算，计算量随批量线性上涨，而权重只读一遍，天平就往算力那边倒。所以一个服务集群里，小批量时是带宽瓶颈，大批量时是算力瓶颈，调度要在这两者之间找平衡点。这个转折点的位置，取决于带宽和算力的比值，不同硬件不一样。

顺着这条线还能解释另一件事：批处理为什么有效。如果一次只服务一个请求，读 140 GB 权重只为了算一个 token，绝大部分带宽都浪费了。如果同时服务 32 个请求，同一份权重读一次，可以给 32 个请求各算一个 token。权重读取的成本被摊了 32 份。

代价是每个请求的 KV 缓存要各存一份，显存占用涨 32 倍。这就把话题引到下一节。

### 上下文为什么按长度收费

上下文贵，有两个来源，性质完全不同。

第一个来源是注意力的计算量。模型在处理一个 token 时，要跟前面每一个 token 做一次相关性计算。序列长度翻倍，两两之间的配对数量翻四倍。这就是所谓的平方增长。4000 个 token 的输入，注意力部分要做大约 1600 万次配对；8000 个 token，是 6400 万次。

这个平方只影响“读入”阶段。模型一次性处理你给的全部输入时，要把所有位置两两算一遍，所以输入越长，这一段的计算量涨得越快。这就是为什么上传一份两百页的 PDF，等首字要等很久。

等到开始逐字生成，情况变了。生成第 N 个字时，前面的内容已经在缓存里，只需要拿当前这个字去跟缓存里的 N 个位置各算一次，是线性增长，不是平方。所以长上下文主要贵在“读进去”的那一刻，不是贵在“写出来”的过程。

第二个来源是 KV 缓存，这个更持久，也更占地方。

算法是这样的：每一层、每一个 KV 头，都要为每个 token 存一份键和一份值。以一个 70B 级的常见配置为例，80 层，8 个 KV 头（这是分组查询注意力，比每个头都存要省很多），每个头的维度是 128。每层每个 token 存两个数（键和值），每个数 2 字节。

算一下：2 乘 80 层，乘 8 个头，乘 128 维，乘 2 字节，等于 327680 字节，大约 320 KB。

一个 token 的缓存是 320 KB。这个数字要记住，后面全靠它。

8000 个 token 的上下文，缓存是 8000 乘 320 KB，等于 2.56 GB。一次请求就吃掉 2.5 GB 显存。

128K 上下文，是 41 GB。这已经超过了一张 80 GB 卡的一半。

一百万 token 上下文，是 320 GB。比模型权重还大一倍多。

这就解释了一件事：为什么“支持一百万 token”是一个很贵的承诺。它不是把窗口调大一点那么简单，它意味着每来一个请求，显存里就要多留出几百 GB。能这么干的系统，要么并发压得极低，要么硬件堆得极多。

### 第一个字慢，后面快

用过的人都注意过一个现象：输入一大段文字，第一个字要等好几秒；一旦开始出字，后面就流畅了。

这两个阶段有名字。第一个字出来的时间叫首字延迟，后面每个字之间的间隔叫出字间隔。它们由完全不同的东西决定。

读入阶段是算力密集的。你给的全部输入可以同时计算，GPU 的上万个核心全部吃满，效率很高。这一段花的时间大致和输入长度成正比：8000 个 token 的输入，在八张卡上大概零点几秒；换成 128K，就是十几秒。

生成阶段是带宽密集的。每出一个字，都要把权重读一遍，而且字与字之间有严格的先后顺序，没法并行。所以出字间隔基本是常数，跟你输入了多长关系不大，跟模型多大、卡有几张、带宽多高关系很大。

这两个阶段的成本结构也不同，这直接决定了定价。

读入阶段的算力利用率高，可以大批量并行。一百个请求的输入，可以拼成一批一次算完，GPU 几乎不浪费。所以输入 token 的边际成本低。

生成阶段没法这么干。每个请求每步只出一个 token，虽然可以批处理，但批处理的规模受显存限制（每个请求的 KV 缓存都要占地方）。而且生成是串行的，一步接一步，中间不能跳过。所以输出 token 的边际成本高。

这就是为什么几乎所有 API 的输出价格都是输入的 3 到 4 倍。不是因为输出更“有价值”，而是因为输出的单位成本确实更高。

### 批处理：把空闲填满

一台八卡的机器，如果一次只服务一个请求，绝大多数时间在等显存。这是巨大的浪费。

批处理（batching）解决的就是这个。把同时到达的多个请求拼成一批，一次读权重，给所有请求各算一个 token。批越大，权重读取被摊得越薄，单位成本越低。

假设 batch 是 32，一次读 140 GB 权重，同时推进 32 个请求。权重成本摊到三十二分之一，单位算力成本降了一个数量级。这就是为什么 API 能卖到每百万 token 一两美元，而你自己拿一张卡跑单请求，算下来要贵几十倍。

要做到这一点，调度得足够细。最简单的方式是攒够一批一起跑，等这一批全部结束再收下一批。问题是请求长短不一：一个只要三十个字的请求，得陪着一个要三千字的请求等到最后，这段时间它占着显存不干活。真实系统用的是连续批处理：每生成一个 token 就看一眼队列，谁结束了就把它踢出去，把空位让给排队的人。这样显存里始终是满的，吞吐能接近理论上限。这是工程细节，但它决定了同样的硬件能服务多少用户，也就直接决定了价格。

但 batch 不能无限大，卡在显存上。

显存的总账是这样：权重 140 GB 固定不动，剩下的全给 KV 缓存。四张 80 GB 卡一共 320 GB，减去 140 GB 权重，再减去临时工作区，大约能拿出 160 GB 给 KV 缓存。

每个请求 8000 token 上下文，占 2.56 GB。160 除以 2.56，约等于 62 个并发。

62 个并发，每个每秒出 30 字，总吞吐是每秒 1860 字。这个数字决定了单位成本。

现在把上下文从 8000 提到 128K，是 16 倍。每个请求的 KV 缓存从 2.56 GB 变成 41 GB。160 除以 41，只能容纳 3 到 4 个并发。

上下文翻 16 倍，并发掉到十六分之一。

这就是那个问题的答案：**长上下文和高并发不能同时便宜，因为它们在抢同一块显存。**

而且这个矛盾是非线性的。上下文从 8K 到 32K，你觉得只是“稍微长一点”，但在显存账本上，并发已经掉了四分之三。要在长上下文下维持并发，只能加卡。加到八张，显存翻倍，并发翻倍，但硬件成本也翻倍，单位成本并没有降。

所以那些“超长上下文”的产品，定价方式往往不是按 token 线性收，而是单独设一个高价档位，或者限制并发。这不是商业策略，是显存账本的直接翻译。

### 价格是怎么标出来的

现在可以把所有东西换成钱。

一台八卡 H100 的机器，租用价格大致是每小时 25 美元，也就是每张卡每小时 3 美元左右。这个价格在过去两年里波动很大，从 2 美元到 8 美元都出现过，取 3 美元是一个中间值。

这台机器在良好批处理下，综合吞吐大约是每秒 5000 个 token。这是个量级估计：八张卡，每张每秒六百多个 token，输入输出混算。

一小时 3600 秒，产出 1800 万个 token。

25 美元除以 1800 万，再乘一百万，得到每百万 token 约 1.4 美元。

这个数字和市面上 70B 级模型的实际报价在同一个量级——每百万输入 token 从零点几美元到两三美元不等。差距来自几个地方：有的厂商自己有卡，折旧算得低；有的用的是更便宜的卡或者更小的模型；有的靠极高的利用率把成本压下去；也有的在亏本换市场。

把这条账反过来用，能得到几个有用的判断。

第一，价格和模型大小大致成正比。参数量翻倍，权重翻倍，每 token 要搬的数据翻倍，成本大致翻倍。这是为什么小模型便宜得离谱：一个 7B 模型，权重只有 14 GB，一张卡能装，吞吐是 70B 的十倍以上，价格能差一个数量级。

第二，输入和输出的价差有物理原因。前面算过，读入阶段算力利用率高、可大批量并行；生成阶段受带宽限制、批处理规模受显存限制。所以输出贵 3 到 4 倍是合理的，如果某家输出只比输入贵一点，要么它在补贴，要么它把输入价格抬高了。

第三，长上下文该单独收费。128K 上下文的请求，KV 缓存是 8K 的 16 倍，并发掉到十六分之一，单位成本涨了一个数量级。按同样的单价卖，是亏的。

反过来说，这也决定了“自己部署还是买 API”的分界线。自己买卡的固定成本很高，而利用率很难做满：白天忙、夜里闲，平均下来可能只有三成。API 提供方把几千个客户的请求混在一起，利用率能到七八成，这个差距比硬件差价大得多。所以只有当天均 token 量足够大、且流量足够平稳时，自建才划得来；量小的时候，自建的单价一定高于 API，哪怕卡是你自己的。

第四，缓存能省钱。如果你的多次请求共享同一段长前缀（比如同一份系统提示、同一份文档），很多系统支持前缀缓存：这段内容只算一次，后面的请求直接复用。对于“同一份长文档问十个问题”这种场景，能省掉九成的输入成本。这也是为什么提示的写法会影响账单——把不变的内容放前面，把变化的内容放后面，缓存才能命中。

回到开头那个团队。他们的账单涨了四倍，现在可以拆开了：输入从 800 涨到 4000，多出来的 3200 个 token 里，有多少是知识库检索塞进来的、有多少是历史对话、有多少是那份三百行的政策文档。如果政策文档每次都全文塞进去，改成按需检索三段，输入能砍掉一多半。如果历史对话只保留最近五轮加一个摘要，又能砍一截。输出从 150 涨到 400，如果去掉“请解释原因”，或者要求“三句话以内”，账单立刻下来。

这些都不是模型能力问题，是用法问题。

下一章讲三种用法：把要求写清楚的提示、用样本改造模型的微调、把外部知识按需取用的检索与智能体。它们的分界线，正好是这一章算出来的三种成本——提示不花钱但占上下文，微调花一次钱换每次更短的提示，检索用一次网络往返换掉一大段塞进上下文的文档。选哪种，取决于你的请求里，钱到底花在了哪一段。
