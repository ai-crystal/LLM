## 一次部署复盘：从 POC 到上线

前面九章是零件。这一章把它们装一台车，看看哪几个零件真的有用。

案例是合成出来的，但每一步的取舍都来自真实项目里反复出现的模式。

### 起点

一个电商客服系统。日请求量从 3 万起步，预期半年后到 30 万。输入平均 1800 token（系统提示 900、订单上下文 600、用户问题 300），输出平均 250 token。

SLO 定得很朴素：首字延迟 p95 小于 1.2 秒，每 token 间隔 p95 小于 60 毫秒，可用性 99.9%。

模型选了一个 32B 的开源模型。理由不是效果最好，而是效果够用、许可证允许商用、社区有现成的推理配置。

### 第一版：能跑，但很贵

最初的部署是最直接的：8 卡一台机器，塞满模型，起一个推理服务，开默认配置。

压测结果：单请求首字 2.8 秒，每 token 95 毫秒，并发 8 时开始排队。

三个问题同时出现：首字慢（因为 1800 token 的预填充要跑一遍）、吞吐低（批没开起来）、并发上限低（缓存吃显存）。

这一版按峰值 60 QPS 估，要十几台机器，成本远超预算。

### 第二步：修调度，收益最大

先做的不是量化，而是把推理引擎换成支持连续批处理和分页缓存的那个。

改动很小：换引擎、调两个参数（最大批、块大小）。结果：同样 8 卡，并发从 8 涨到 40，吞吐涨 2.6 倍，每 token 间隔降到 55 毫秒。

这一步收益最大，成本几乎为零。经验是：**先用好引擎，再谈模型优化。**

### 第三步：前缀缓存，把系统提示的成本去掉

系统提示 900 token，每条请求都一样。开前缀缓存后，这部分只在缓存冷的时候算一次。

命中率实测 78%（有 22% 因为提示里有动态内容而失配）。首字延迟从 1.9 秒降到 1.1 秒，预填充算力省了三成。

顺手改了一件事：把提示里的"当前时间"从最前面挪到最后面。原来它在系统提示的第二行，导致每条请求的前缀在几十个 token 处就分叉，命中率只有 12%。

一个小改动，命中率从 12% 涨到 78%。这是这一册里性价比最高的技巧。

### 第四步：多轮对话的账

客服对话平均 2.3 轮。第一版里，每一轮都重算全部历史，越聊越慢。

前缀缓存直接解决了这个问题：第二轮只算新增的用户消息，预填充时间从 1.9 秒降到 0.3 秒。

用户体验的变化比数字更明显：原来第三轮开始明显卡顿，改完之后一直很顺。

### 第五步：量化，谨慎地做

到这里，显存还是紧：40 并发时缓存占掉了一大半，批开不大。

试了 INT8 量化（权重和缓存都做），显存省了一半，并发从 40 涨到 70，吞吐涨 60%。

然后测质量。通用基准掉得不多，但格式遵循出了问题：要求输出 JSON 的请求里，有 3% 出现了字段缺失。这在客服场景里不可接受。

最后换成"权重 INT8、缓存 FP16"，格式问题消失，收益打了折（并发到 55）。这个取舍值得记：**量化的风险不在平均能力，在边缘行为。**

### 第六步：评估 PD 分离，决定不做

首字延迟的 p95 仍然偶尔超标（1.4 秒），因为长订单上下文的预填充会把解码卡住。

按第八章的标准评估：预填充占比 28%（未过三成）、只在一台机器内（不需要跨机）、长提示比例 6%。结论是干扰存在但不严重，分离的收益抵不过复杂度和传输开销。

替代方案是用引擎自带的切块预填充，把长预填充切成 512 token 一块，块之间插入解码。改完 p95 降到 1.1 秒，改动只有一行配置。

这一条说明：**架构级的改动要留到最后，先用现成的调度手段。**

### 第七步：投机解码，只在一个场景开

C 端页面的输入很短（平均 40 token），输出是模板化的回复，重复率高。这个场景试了投机解码：接受率 0.76，加速 1.9 倍。

但批量导出的场景（一次生成几十条回复）开了反而慢，因为批大小是 32，解码已经接近算力受限。

最终按路由分开配置：短请求开投机，批量任务关。同一个模型，两套参数。

### 最终配置与数字

| 指标 | 第一版 | 上线版 |
|---|---|---|
| 首字延迟 p95 | 2.8 s | 1.1 s |
| 每 token 间隔 p95 | 95 ms | 48 ms |
| 单机并发 | 8 | 55 |
| 单机吞吐 | 210 token/s | 1400 token/s |
| 峰值所需机器 | 14 | 4 |

成本降到原来的三成左右。收益来源大致是：调度 40%，前缀缓存 30%，量化 20%，切块预填充 10%。

### 复盘：哪些做对了，哪些是弯路

**做对的：** 先换引擎再优化模型；先算账再改架构；每次只改一件事并单独测；量化之后专门测格式遵循。

**弯路：** 一开始想直接上 PD 分离，花了三周做原型，收益不足 10%；试过一套自研调度器，性能不如开源引擎；有段时间迷信"更大的批"，结果 p99 延迟超标，被迫回退。

**最值钱的一条经验：** 优化之前先量出瓶颈在哪。这个案例里，前三步（换引擎、前缀缓存、改提示顺序）几乎不花钱，却拿走了七成收益；而花钱最多的一步（量化）只占两成，还带来质量风险。

### 这一册的收尾

把十章连起来，只有一句话：**推理是在带宽、显存、延迟三者之间做分配，每一个技术都在挪动其中一个量。**

预填充吃算力，解码吃带宽；缓存省时间但吃显存；批处理提高带宽利用率但拉长延迟；量化缩小读取量但牺牲精度；投机解码用并行换串行，但依赖场景。

没有万能的优化。能做的只有：量出瓶颈、选一个手段、单独测、再量。
