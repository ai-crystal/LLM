## 前缀复用：同一段开头不必算两遍

一个客服系统，每条请求前面都挂着两千 token 的系统提示：角色设定、可用工具、返回格式、注意事项。

每条请求都要为这段前缀跑一次预填充。一天十万次请求，等于把同一段文字算了一亿次。

这段计算完全多余。前缀相同，中间结果就相同。把它存下来复用，叫前缀缓存。

### 为什么前缀可以复用

注意力的结果只依赖"当前 token 和它前面所有 token"。所以只要前缀一模一样，每个位置的 $K$ 和 $V$ 就一模一样，跟后面接什么无关。

这意味着两件事：

第一，同一段前缀的 KV 可以存一次、用很多次；
第二，复用的单位不是"整段提示"，而是"从开头起算、完全一致的那部分"。前缀在第几个 token 开始分叉，缓存就在那里失效。

第二条是实践中最容易出错的地方。有人在系统提示里插了当前时间（"现在是 2026-11-20 14:03:22"），于是每一秒的前缀都不同，缓存命中率掉到零。

### 多轮对话是最自然的场景

一轮对话结束后，下一轮的提示是"上一轮全部内容 + 新的用户消息"。前缀完全一致，只有最后几十个 token 是新的。

所以多轮对话的理想情况是：第一轮付一次全量预填充，之后每轮只算新增部分。第十轮时，如果前九轮共 4000 token，这一轮只需要算新增的 200 token——预填充成本降了 95%。

没有前缀缓存时，每轮都要重算全部历史，成本随轮数线性增长；有了它，成本基本是常数。这对长对话的体验影响非常大：同样是十轮，一个越聊越慢，一个一直很快。

### 怎么匹配

实现上不是逐字节比较，而是按块。

把 token 序列切成固定大小的块（比如 16 个），每块算一个哈希值，哈希的输入包括"上一块的哈希 + 本块的 token"。用链式哈希的原因是：块的内容相同但位置不同，语义也不同，链式可以保证只有从头完全一致的前缀才匹配。

请求进来时，从头逐块查表：命中就跳过这块的计算，直到第一块没命中为止。命中的块直接复用缓存，后面的块照常算。

淘汰用 LRU：长期没人用的前缀块回收。实践中会按"块被复用的次数"加权，因为系统提示这类高频前缀应该比一次性文档活得更久。

### 收益有多大

取决于命中率，而命中率取决于前缀的一致性。

| 场景 | 前缀占比 | 典型命中率 | 预填充节省 |
|---|---|---|---|
| 固定系统提示 | 60%–90% | 高 | 50%–80% |
| 多轮对话 | 随轮数升高 | 高 | 70%–95% |
| 同一文档多问题 | 50%–80% | 中 | 40%–70% |
| 一次性长文摘要 | 0 | 无 | 0 |

最后一行值得注意：单次请求、内容各不相同时，前缀缓存完全帮不上。这决定了它不是一个"通用加速"，而是一个"场景加速"。

### 一个顺序上的讲究

做检索增强的系统，提示通常由几段拼成：系统提示、检索到的文档、用户问题。

顺序会影响缓存。如果把用户问题放在最前面，那么每条请求的第一个块就不同，后面全部失配。正确的顺序是从稳定到易变：系统提示 → 文档 → 问题。这样系统提示和相同文档都能命中。

同一份文档被多个用户问到时，这种排法还能让文档部分跨请求复用——前提是文档本身不含隐私内容，或者缓存做了租户隔离。

### 隔离与侧信道

跨请求共享缓存能省很多，但有两个风险。

**数据串台。** 如果缓存按内容哈希匹配，而两个租户恰好有相同前缀，理论上可以共享。但一旦匹配逻辑出错，就可能把 A 的上下文给 B 用。工程做法是给缓存加租户标签，只共享明确标记为公共的部分。

**侧信道。** 攻击者可以通过"响应快不快"推断某段内容是否被缓存过，从而推断别人是否问过某个问题。这类攻击在论文里出现过，实现上很脆弱，但在高敏感场景里需要考虑。

### 和批处理的关系

前缀缓存和连续批处理解决的是不同问题：前者减少"要算的量"，后者提高"算的时候的利用率"。两者会互相影响：

- 命中的块越多，预填充越短，批里解码的占比越高，调度越顺；
- 但缓存本身占显存，块表也有开销，挤占的是并发数。

工程上要留出一部分显存给缓存（常见配置是 10%–20%），并按命中率动态调整。命中率高时多留，命中率低时还给 KV。

### 小结

前缀复用的本质是"不要把算过的东西再算一遍"。它不需要改模型，不需要改硬件，只需要把请求组织好——但恰恰是"组织好"这件事，很多系统没做。
