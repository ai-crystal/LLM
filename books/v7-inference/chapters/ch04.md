## 前缀复用：同一段开头不必算两遍

### 每天把同一段两千字算一亿次

一个客服系统接进了电商后台。每条请求前面挂着一段两千 token 的系统提示：角色设定、可调用的七八个工具、返回格式、十几条业务规则、五个示例问答。

这套提示写得很认真，效果也确实好。上线一个月后看账单，预填充的算力占了整机计算量的六成。

把提示拆开看就明白了。两千 token 里，一千八百个是固定内容，两百个是订单上下文和用户问题。也就是说，**每条请求里九成的预填充是在算一段从来没变过的文字。**

十万次请求一天，等于把同一段文字算了一亿遍。这些计算的结果每次都完全一样，因为它们只依赖前缀本身。

这一段省下来，账立刻变好看。7B 模型算 1800 token 的预填充是

$$2\times7\times10^{9}\times1800=2.5\times10^{13}\ \text{FLOPs}$$

除以 $1.4\times10^{14}$ 的有效算力，0.18 秒。一天十万次就是五小时的卡时。按单卡每秒一千个输入 token 的吞吐能力算，这部分工作量正好是一张 A100 跑满一整天。

而如果把它缓存下来，这部分时间从 0.18 秒降到几毫秒。

### 为什么前缀可以复用

注意力的结果只依赖"当前 token 和它前面所有 token"。这句话有两个推论。

第一，只要前缀一模一样，每个位置的 $K$ 和 $V$ 就一模一样，跟后面接什么完全无关。所以同一段前缀的缓存可以存一次、用很多次。

第二，复用的单位不是"整段提示"，而是"从开头起算、完全一致的那部分"。前缀在第几个 token 开始分叉，缓存就在那里失效。

第二条是实践中最容易踩的地方。有人在系统提示里插了当前时间，"现在是 2026-11-20 14:03:22"，本意是让模型知道日期。结果每一秒的前缀都不同，缓存命中率掉到个位数。

算一下损失多少。那段时间和它的标签大约占 40 个 token，位置在系统提示的第二行。于是每条请求只有前 40 个 token 能命中，后面 1760 个全部要重算：

$$\text{可复用比例}=\frac{40}{1800}\approx 2\%$$

实测能到 12%，因为同一秒内进来的请求时间戳相同，能互相命中。但 12% 和 88% 的差距，就是"每天一张卡白烧"和"每天省一张卡"的差距。

修法只有一个：**把动态内容挪到提示的最后面。** 系统提示、工具定义、业务规则、示例问答全部放在前面，订单信息、时间、用户 ID 全部放在后面。同样的文字，命中率从 12% 跳到 78%。这是这一册里性价比最高的一个改动，成本是改一段字符串拼接。

### 多轮对话的账

多轮对话是最自然的复用场景。一轮结束后，下一轮的提示是"上一轮全部内容 + 新的用户消息"。前缀完全一致，只有最后几十个 token 是新的。

算一下没有缓存时，十轮对话要花多少预填充。

假设每轮用户输入 100 token，模型回答 300 token，系统提示 900 token。第二轮输入是"系统提示 + 第一轮的问答（400） + 新问题（100）"，大约 1400 token。第三轮 1800，第四轮 2200，以此类推。

十轮的总预填充量

$$900+1400+1800+\cdots+4500\approx 27000\ \text{token}$$

有缓存之后，第一轮算 1300 token，之后每轮只算新增的 400 token：

$$1300+9\times400=4900\ \text{token}$$

差 5.5 倍。换成时间，7B 模型上大概从 3.8 秒降到 0.7 秒。

更重要的是曲线形状。没有缓存时，预填充量随轮数平方增长（每轮都要重算全部历史）；有缓存时是线性的（每轮只算新增）。用户感受到的差别不是"第十轮慢一点"，而是"聊到第五轮开始明显卡，第八轮不可用"。

有一类失败场景正好相反。有人发现"多轮对话里第二轮总是很慢"，查了半天以为是缓存没生效。实际原因是他们的客户端每轮都会在开头重新拼一段"当前会话摘要"，而摘要由模型生成，每次措辞略有不平。整段前缀从第一个字就不一致，缓存全部失效。

修法是把摘要也挪到末尾，或者让摘要的生成变成确定性的（同样的输入产出同样的字）。**缓存的敌人不是"内容变"，是"内容在靠前的位置变"。**

### 算一遍：命中率与节省

收益取决于命中率，而命中率取决于前缀的一致性。

| 场景 | 前缀占比 | 典型命中率 | 预填充节省 |
|---|---|---|---|
| 固定系统提示 | 60%–90% | 高 | 50%–80% |
| 多轮对话 | 随轮数升高 | 高 | 70%–95% |
| 同一文档多问题 | 50%–80% | 中 | 40%–70% |
| 模板化批量生成 | 80%–95% | 极高 | 80%–90% |
| 一次性长文摘要 | 0 | 无 | 0 |

节省的比例不能直接相乘，得乘上一个效率折扣。因为命中的部分省掉了计算，但块表查询、哈希计算、缓存内存都要成本。经验上实际节省约等于"命中率 × 前缀占比 × 0.9"。

拿系统提示那行代入：命中率 78%，前缀占比 90%（1800/2000），

$$0.78\times0.90\times0.9\approx 63\%$$

也就是预填充从 0.2 秒降到 0.07 秒。TTFT 里省下 0.13 秒，看着不多，但如果机器上压着一百个请求，省下的算力能多服务六十多个请求。

表格最后两行值得对比。同样是"前缀复用"，一次性长文摘要完全无效，模板化批量生成能省八成。差别不在技术，在流量形态。**前缀复用不是一个通用加速，是一个场景加速。**

### 怎么匹配

实现上不是逐字节比较，而是按块。

把 token 序列切成固定大小的块，比如 16 个 token，每块算一个哈希值。哈希的输入不是"这一块的内容"，而是"上一块的哈希 + 这一块的 token"。这叫链式哈希。

为什么要链式？因为块的内容相同但位置不同，语义也不同。"你好"出现在第 5 个 token 和第 2000 个 token，前面接的东西完全不同，最后一层的键值也不同。链式哈希保证只有从开头起算、逐块完全一致的前缀才能匹配，任何一处不同都会让后面所有块的哈希都变。

请求进来时，从头逐块查表。命中就跳过这块的计算，把缓存直接接上；直到第一块没命中为止，后面的块照常算。

块大小是个权衡。块小，命中粒度细，能多省一点；但块表项多，哈希和查表开销大，管理的复杂度也高。16 个 token 是常见选择，也有用 8 或 32 的。混合长度前缀（比如每条请求的系统提示长度不一）在块边界上容易浪费，这时候按"最短公共前缀"对齐会更省。

也有引擎在块哈希之外再加一层"内容哈希"，用整段前缀的指纹做一级索引，减少逐块比较的次数。这类优化在命中率高的场景里能省几个百分点的调度开销。

### 淘汰：谁该活得更久

缓存不能无限大，得有淘汰策略。

朴素的是 LRU（最近最少使用）：最久没人用的块回收。问题在于"最近用过"不等于"以后还会用"。一段一天只被访问一次的公共政策文档，和一小时前被某个人用过的临时草稿，LRU 会保留后者，丢掉前者。

更好的做法是按"块被复用的次数"加权。系统提示这类每秒被命中几十次的前缀，应该比一次性文档活得久得多。实现上给每个块记一个命中计数，淘汰时按"最近使用时间 × 命中次数"排序。

还有一条经验：**优先保留靠前的块。** 因为前缀是从头开始匹配的，一个请求命中多少块取决于它能连续命中到第几块。第一块被淘汰，后面全废；最后一块被淘汰，只损失一块。所以按块位置给权重，靠前的块权重高，能明显提升有效命中率。这个细节在论文和开源实现里都有讨论，效果比调 LRU 参数更明显。

### 顺序上的讲究

做检索增强的系统，提示通常由几段拼成：系统提示、检索到的文档、用户问题。

顺序会直接决定缓存命中率。如果把用户问题放在最前面，每条请求的第一个块就不同，后面全部失配，命中率为零。

正确的顺序是从稳定到易变：

$$\text{系统提示}\rightarrow\text{工具定义}\rightarrow\text{文档}\rightarrow\text{对话历史}\rightarrow\text{用户问题}$$

这样系统提示几乎总是命中，工具定义总是命中。文档部分在同一份文档被多个用户问到时也能跨请求复用。

还有个更细的技巧：如果检索到的是多份文档，把它们按"内容指纹"排序再拼接。这样同一批文档以不同顺序被召回时，前缀仍然一致。代价是排序要花一点 CPU，收益是命中率从零变成大部分。

### 缓存要占多少显存

缓存不是免费的，它吃掉的是本来能给 KV 的显存。

第二章算过，一张 A100 跑 7B，42 GB 能给缓存，4096 token 一条要 2 GB，能放 21 条。如果拿 15% 出来做前缀缓存，就是 6.3 GB，少放 3 条请求。

这笔交易划不划算，取决于命中率。命中率 78% 时，每条请求的预填充从 0.2 秒降到 0.07 秒，机器能多服务 60% 的请求；代价是并发从 21 降到 18，少 14%。净赚。

命中率 10% 时，省下的算力可以忽略，纯亏 14%。

所以工程上常见两种做法。一种是固定比例（10% 到 20%），简单但可能不优。另一种是动态调整：监控命中率，命中率高时多给，命中率低时回收给 KV。第二种更复杂，但能吃到两个方向的收益。

还有一个容易漏的成本：**块表本身的内存和查询开销。** 每秒几万次查询，哈希计算和表查找是实打实的 CPU 开销；如果放在 GPU 上做，又要占一点点显存和算力。这部分在低延迟场景里能占到几百微秒，值得单独打点。

### 算一算：命中率能换成多少台机器

把命中率折成钱，需要一个参系：预填充占总计算的比例。前面那个客服系统是六成，后面用这个数。

不改任何东西时，服务 58 请求每秒的峰值需要多少预填充算力？输入 2000 token，每秒 11.6 万输入 token。单卡每小时能算 $1000\times3600=3.6\times10^6$ 个输入 token，所以需要

$$116000\times3600/3.6\times10^{6}\approx 116\ \text{张卡}$$

这是一笔很大的开销。开前缀缓存、命中率 78% 之后，实际需要算的输入 token 降到 22%，卡数降到

$$116\times0.22\approx 26\ \text{张卡}$$

再算上缓存占显存带来的并发损失（约 14%，按比例折回 4 张），净省八十多张卡。

这个换算里有个陷阱：**命中率不是常数，它随流量涨而涨。** 请求越多，同一段前缀被命中的机会越多，缓存也越容易保温。所以小流量时算出来的收益会偏低，上线后往往比预估的好；反过来，做容量规划时不要拿压测的小流量去推大流量的命中率，会高估成本。

### 与分页的配合：共享的块

前缀缓存和分页缓存是同一套块机制的两个用途，放在一起才能看出省在哪。

分页把显存切成固定大小的块，每个请求一张块表。前缀缓存做的事是：当两条请求的前缀块完全相同时，让它们的块表指向同一批物理块，并把引用计数加一。

一个具体例子。一百个用户共享同一段 1800 token 的系统提示，块大小 16，需要 113 个块。

不共享：$113\times100=11300$ 个块。7B 模型一块是 $16\times512\ \text{KB}=8$ MB，共 90 GB，一张卡装不下。

共享：113 个块，不到 1 GB。

这就是为什么长对话场景里，“前缀复用省显存”的收益经常比“省算力”更大。系统提示、工具定义、RAG 的公共文档部分，全部只存一份。引用计数归零时才回收，回收逻辑和普通块一样。

代价是实现变复杂：块要能被多条请求引用，引用计数要原子操作，回收时不能有请求还在读。写入也要小心，前缀块是只读的（它们不会再变长），所以可以安全共享；可写的尾部块不能共享。这条界线划清楚，实现就不难。

### 隔离与侧信道

跨请求共享缓存能省很多，但有两个风险。

**数据串台。** 如果缓存按内容哈希匹配，两个租户恰好有相同前缀（比如都用同一套系统提示），理论上可以共享，也确实应该共享。但一旦匹配逻辑出错，就可能把 A 的上下文给 B 用。工程做法是给缓存加租户标签，只共享明确标记为公共的部分；系统提示算公共，用户文档和个人对话历史算私有。

**侧信道。** 攻击者可以通过"响应快不快"推断某段内容是否被缓存过，从而推断别人是否问过某个问题。具体做法是构造一个候选前缀，发一条请求，测首字延迟；如果延迟明显低，说明前缀在缓存里，也就说明有人最近问过类似的东西。这类攻击在论文里出现过，实现上很脆弱（需要精确的计时和高频请求），但在医疗、法务这类高敏感场景里需要考虑。

缓解手段有两个：缓存命中带来的时间差里加一点抖动，让攻击者测不准；或者对私有内容干脆不做跨请求共享，只做同用户内的复用。后一种会损失一部分收益，但边界清楚。

### 什么时候它不管用

**一次性内容。** 每条请求的提示都不一样，命中率为零。这类流量加前缀缓存只是多了一层查表开销。

**前缀很短。** 系统提示只有 50 token，命中省下的计算还不如查表的开销。

**缓存太碎。** 每个用户有自己的一套几百 token 的前缀，几百个用户就有几百套，缓存全被这些碎片占满，互相挤掉，命中率上不去也淘汰不掉。这种情况要给"低频前缀"设一个最小使用次数门槛。

**预填充不是瓶颈。** 如果流量是长输出短输入，预填充只占计算量的一小部分，省下的那点算力感知不到。

**缓存命中但质量变差。** 有一种隐蔽的失效：命中逻辑写得不对，把“前缀相似但不相同”的块当成命中，于是模型看到了别人的上下文。表现是回答偶尔驴头不对马嘴，比例很低，很难复现。防御手段是严格按链式哈希匹配，宁可不命中也不能错命中；同时在开发环境里加一个校验开关，命中后把块内容重新哈希比对一次，只在上线前开，用来抓这类 bug。

判断方法：看预填充占总计算的比例。超过四成，前缀复用大概率值得做；低于两成，先去做别的。

### 一项免费的优化

前缀复用的本质是"不要把算过的东西再算一遍"。它不需要改模型，不需要换硬件，只需要把请求组织好。

但恰恰是"组织好"这件事，很多系统没做。常见的有三种：提示里的时间戳放在最前，摘要每轮重写，多份文档的拼接顺序随机。这三种问题都不报错，只是账单悄悄变厚。

以及一个容易被忽略的连带好处：命中的前缀不需要重新分配 KV 块，只做引用计数共享。这让长对话场景的显存占用也降下来——十个用户共享同一段系统提示的缓存，就只存一份。这一层收益经常比省算力更大。

有一个数字能总结这一章：一段 1800 的固定提示，命中率从 12% 修到 78%，改动是把一个时间戳从第二行挑到最后一行。代码改动十几行，机器少买六成。这类优化的共同特征是“发现它需要算账，修它只需要改对地方”，而发现它的前提是你先知道预填充占了多少。
