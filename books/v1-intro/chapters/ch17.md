## 接口长什么样：一次调用到底发了什么

前面说“调用一次模型”，这件事在技术上是一次 HTTP 请求。你发一段 JSON 过去，它回一段 JSON 回来。

这一章把这个来回拆开看。搞清它长什么样，你就不会被“OpenAI 兼容”“A 社接口”“多模态接口”这类名词绕住——它们说的都是同一件事的不同方言。

### 最小的一次调用

以最常见的对话接口为例，请求体大致是这样：

```json
{
  "model": "some-model-v1",
  "messages": [
    {"role": "system", "content": "你是一个简洁的助手。"},
    {"role": "user",
     "content": "用一句话解释什么是梯度下降。"}
  ],
  "temperature": 0.7,
  "max_tokens": 200
}
```

四个字段就够跑起来：`model` 指定用哪个模型，`messages` 是对话历史，`temperature` 控制随机程度，`max_tokens` 限制输出长度。

返回长这样：

```json
{
  "id": "chatcmpl-abc123",
  "choices": [
    {"index": 0,
     "message": {
       "role": "assistant",
       "content": "沿着损失函数下降最快的方向小步走。"
     },
     "finish_reason": "stop"}
  ],
  "usage": {
    "prompt_tokens": 38,
    "completion_tokens": 22,
    "total_tokens": 60
  }
}
```

三个地方值得记住。回答正文在 `choices` 里，取第一项的 `message` 即可。`finish_reason` 告诉你为什么停：`stop` 是正常说完，`length` 是撞到 `max_tokens` 被截断。`usage` 是计费依据——输入和输出是分开计价的。

`messages` 里的 `role` 只有三种基本角色：`system` 是全局设定，`user` 是你，`assistant` 是模型的回复。多轮对话的做法就是把上一轮的 assistant 回复也塞回这个数组，模型没有“记忆”，它只是每次都在读这一整个数组。

### 流式：为什么字是一个一个出来的

上面的接口是“等全部生成完，一次性返回”。但产品里你要的是逐字出现的效果，那用的是流式版本：请求里加 `"stream": true`。

这时返回的不再是一个 JSON，而是一串由 `data:` 开头的事件，每个事件里带一个增量片段：

```text
data: {"choices":[{"delta":{"content":"沿着"}}]}
data: {"choices":[{"delta":{"content":"损失"}}]}
data: [DONE]
```

前端把每个 `delta.content` 追加到屏幕上，就有了“打字机”效果。工程上要注意两件事：一是要处理 `[DONE]` 结束标记，二是网络中断时已经收到的部分不能算完整回答。

### A 社接口的差别

Anthropic 的 Messages 接口（业内常简称“A 社接口”）解的是同一个问题，但字段形状不同。同样的请求会写成：

```json
{
  "model": "claude-like-model",
  "system": "你是一个简洁的助手。",
  "messages": [
    {"role": "user", "content": "用一句话解释梯度下降。"}
  ],
  "max_tokens": 200
}
```

三个关键差异：

**系统提示是独立的顶层字段**，不放在 `messages` 里。这反映了不同的设计取向：OpenAI 把 system 当成一条特殊消息，Anthropic 把它当成配置。

**`max_tokens` 是必填的**。OpenAI 侧可以省略（有默认值），A 社侧不写会直接报错。迁移代码时这是最常见的第一个 400。

**返回结构是内容块数组**，不是单个字符串：

```json
{
  "content": [
    {"type": "text", "text": "沿着梯度下降的方向小步走。"}
  ],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 38, "output_tokens": 22}
}
```

这里的内容是 `content` 数组里一个个“块”，因为多模态、工具调用、思考过程都要塞进去。`stop_reason` 对应 OpenAI 的 `finish_reason`，值不一样（`end_turn` / `max_tokens` / `tool_use`）。

流式也不一样：A 社发的是带类型的事件，开始、增量、结束各一种，而 OpenAI 风格是统一的增量块。字段名不同，但每一条都能对上。

### 一张对照表

把两家的核心概念并排放，能省掉大量“这两个是不是一个东西”的困惑：

| 概念 | OpenAI 风格 | Anthropic 风格 |
|---|---|---|
| 系统提示 | `messages` 里一条 `role: system` | 顶层 `system` 字段 |
| 消息内容 | `content` 字符串（或数组） | `content` 块数组 |
| 最大输出 | `max_tokens` 可省略 | `max_tokens` 必填 |
| 停止原因 | `finish_reason` = `stop`/`length` | `stop_reason` = `end_turn`/`max_tokens` |
| 计费字段 | `usage.prompt_tokens` / `completion_tokens` | `usage.input_tokens` / `output_tokens` |
| 工具调用 | `tools` + `tool_calls` | `tools` + `tool_use` 内容块 |
| 流式格式 | `choices[].delta` | 带类型的事件（`content_block_delta`） |

记住这张表的意义不在背字段，而在理解一件事：**两家定义的是同一类接口，差别在字段形状**。你在工程里遇到的所有“兼容层”，本质就是在这张表上做翻译。

### 让它调工具与固定格式

除了说话，接口还负责另外两件常被用到的事。

**工具调用。** 你在请求里多给一个 `tools` 数组，告诉它“你有这些函数可用”：

```json
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "query_order",
      "description": "按订单号查询状态",
      "parameters": {
        "type": "object",
        "properties": {
          "order_id": {"type": "string"}
        }
      }
    }
  }]
}
```

模型不会真的去查，它只回一个“我想调这个函数”的意愿：

```json
{
  "tool_calls": [{
    "id": "call_1",
    "function": {
      "name": "query_order",
      "arguments": "{\"order_id\": \"OD123\"}"
    }
  }]
}
```

真正的执行在你的代码里。你跑完查询，把结果作为一条 `role: tool` 的消息塞回去，再请求一次，模型才会用这个结果回答。所以“模型会调工具”其实是个循环：它说调什么，你执行，你把结果还给它。

A 社的写法不同：工具仍然叫 `tools`，但模型的意图出现在 `content` 数组里的一个块，类型是 `tool_use`，带回的也是一个块，类型是 `tool_result`。逻辑一模一样，只是形状不同。

**固定格式。** 希望它返回 JSON，而不是夹着自然语言的段落，用 `response_format`：

```json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "reply",
      "schema": {
        "type": "object",
        "properties": {
          "sentiment": {"type": "string"}
        },
        "required": ["sentiment"]
      }
    }
  }
}
```

传了 schema，服务端通常会在解码阶段限制可选 token，保证输出合法；没传时只能靠提示词“请返回 JSON”，而模型仍可能多写一句“好的，以下是”。这个区别在工程上很实在：前者不用写容错解析。

### 多模态请求长什么样

发一张图，`content` 就从字符串变成一个数组：

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "这张图里的是什么产品？"},
    {"type": "image_url",
     "image_url": {"url": "data:image/png;base64,iVBOR..."}}
  ]
}
```

图片可以内联成 base64（简单，但请求体大），也可以先上传再传一个 URL（省带宽，但多一步）。A 社的写法是把 `image` 作为一个块，`source` 里写 `base64` 或 `url`。

一个实际影响成本的细节：图片按 token 计费，而 token 数取决于分辨率。同一张图，缩到 336 像素和原图送进去，费用可能差四到六倍。所以多模态应用通常先压缩，需要看细节时才传原图。

### 报错时看哪个字段

接口报错的 HTTP 状态码只有几种，含义稳定：

| 状态码 | 常见原因 | 怎么办 |
|---|---|---|
| 400 | 参数不合法（缺 `max_tokens`、字段名拼错、图片格式不认） | 看错误体里的 `message`，它通常直接指出哪个字段 |
| 401 | 密钥错或已失效 | 换 key，别重试 |
| 403 | 无权限（模型未开通、区域限制） | 查控制台权限 |
| 404 | 模型名写错，或路径不是 `/v1/chat/completions` | 对照兼容清单 |
| 429 | 限流或余额不足 | 指数退避重试；仍失败就看配额 |
| 500/529 | 服务端故障或过载 | 重试，并准备降级到备用供应商 |

一个经验：**400 永远不要重试**。参数错了，重试一百次也是同样的错，只会把日志刷满。

### 为什么会有“OpenAI 兼容”

过去两年，几乎所有开源的推理引擎（vLLM、SGLang、Ollama、LM Studio）、云厂商的托管服务、国产模型 API，都提供一种叫“OpenAI 兼容”的接口。

原因很实际：OpenAI 的接口出现最早、生态最大，绝大多数 SDK、框架、示例代码都是按它写的。一个新服务只要说“兼容 OpenAI”，用户就能把原来的代码只改两个变量——`base_url` 和 `api_key`——直接跑起来：

```python
client = OpenAI(
    base_url="https://your-provider.example/v1",
    api_key="sk-...",
)
```

这两个变量是“兼容”的全部含义：路径按 `/v1/chat/completions` 走，请求与响应按 OpenAI 的字段形状走。

但“兼容”是个程度词，不是开关。实际差异集中在三处：

**参数子集。** 有的服务不认 `response_format`（结构化输出），有的不认 `logprobs`，有的支持 `tools` 但只支持单轮。传了不认识的参数，有的忽略、有的直接 400。

**行为差异。** 同样传 `temperature: 0`，有的服务真的是贪心解码，有的仍然是采样；“最大输出”有些服务把思考过程的 token 也算进去，有些分成两段计。

**错误码。** 429 表示限流、400 表示参数错、401 表示密钥错、500 表示服务端错——这套约定大家都遵守，但错误体里的细节字段各家不同。

判断一个“兼容”接口能不能直接换，最省事的办法是三步：先用官方 SDK 跑一次最简请求；再把你要用的参数逐个加上；最后压一轮并发看限流行为。三步都过，才算真兼容。

### 除了对话，还有哪些接口

日常会碰到的另外几类：

**向量（embeddings）。** 传一段文本，回一个向量。检索系统的基础。注意它通常按 token 计费，且不同模型的向量维度不同、不可混用。

**重排（rerank）。** 传一个问题和一批候选段落，回一个排序。比向量检索准，比大模型便宜。

**语音（transcribe / speech）。** 一个把音频转文字，一个把文字转音频。前者按音频时长计费，后者按字符数。

**图像生成。** 传一段描述，回一张图（可能是链接，可能是 base64）。按张数或像素计费。

**审核（moderation）。** 传一段文本，回“有没有违规、属于哪一类”。便宜、快，适合放在输入输出的两端。

这些接口的形状各不相同，但套路一样：请求是 JSON（或表单），响应里有一个“结果”字段和一个“用量”字段。

### 工程上的四件事

接口本身很简单，出事的地方都在调用侧。

**密钥不能出现在前端。** 浏览器里能看到的 key 等于公开的 key。正确做法是自建一个后端做转发，前端只调自己的后端。

**超时要分层。** 连接超时、首字超时、整体超时是三个不同的数。聊天场景里首字超时通常设 10 到 30 秒，整体超时按最长回答估。只设一个总超时，会出现“用户等了半分钟然后什么都没看到”。

**429 要退避重试。** 撞上限流不要立刻重试，用指数退避加随机抖动（比如 1 秒、2 秒、4 秒，各加一点随机），并且设一个最大重试次数。无脑重试会把限流变成雪崩。

**成本要能归因。** 每次调用把 `usage` 记下来，按用户、按功能、按模型分组。没有这层数据，一个月后你只知道总账单，不知道钱花在哪。

### 本地跑一个：兼容接口最实用的地方

想不花钱先试试，可以本地起一个服务。两条路最常见。

**Ollama。** 装完拉一个模型就能跑，它在本地开一个端口，同时提供一套 OpenAI 兼容的接口：

```python
client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",
)
```

代码和调云端一模一样，只改了两行。对入门来说这是最便宜的学习方式：不需要注册、不产生费用、可以随意试错。

**vLLM。** 团队共享时用这个。启动时指定模型，它会开一个兼容服务，支持并发、连续批处理、流式。生产环境里“自建推理 + 兼容接口”是很常见的形态：对外看起来是 OpenAI，里面跑的是自己的卡。

这两条路说明了一件事：**接口已经变成一层抽象**。上面的应用不需要知道模型跑在哪，只要它说同一套方言。这也是为什么“兼容 OpenAI”会成为行业默认。

### 选 SDK 还是直接发 HTTP

两者都行，看场景。

**用官方 SDK。** 它会帮你处理重试、流式解析、超时、类型校验，代码短。代价是多一个依赖，且 SDK 版本与接口版本要对得上——两者错位时，报错信息往往很难读。

**直接发 HTTP。** 适合跨语言、轻依赖、或者需要精细控制超时的场景。你要自己处理 SSE 解析（按行切分、去掉 `data: ` 前缀、遇到 `[DONE]` 停），也要自己实现退避重试。

一个常见的折中：用 SDK，但把重试关掉、自己包一层——因为默认重试策略往往不适合你的限流配额。

### 三个常见误解

**“兼容就是完全一样”。** 不是。参数子集、默认值、计费口径都可能不同，换供应商必须重新测。

**“换个模型只要改 `model` 字段”。** 大多数情况如此，但输出质量、格式遵循、工具调用能力都会变，线上表现要重测。

**“流式就是快”。** 流式不会让总耗时变短，只是让用户更早看到第一个字。总 token 数、总费用都不变。

### 记住这三件事

一、所谓“接口”，就是一段 JSON 进、一段 JSON 出；`messages` 是历史，`usage` 是账单。

二、OpenAI 风格与 A 社风格是同一件事的两种方言，差别在字段形状；所谓“兼容”，是按 OpenAI 的形状来。

三、兼容不等于相同，换供应商必须重测参数、行为和错误码。
