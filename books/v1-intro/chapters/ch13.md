## 会写代码

一个运维工程师要给日志做个小工具：读 nginx 的 access.log，按小时统计 5xx 的占比，输出 CSV。他把需求打成一段话，模型给了六十行，参数解析、正则、分桶、除零保护、CSV 写入都有。他改了两行路径，跑通了。

同一天下午，他要在公司的主仓库里修一个 bug：某个接口在并发超过 50 时会返回空列表。仓库有二十万行代码，二十几个内部库，还有一堆“为什么这么写”的历史决定。他把相关文件贴进去，模型给了三版修改，每版都能解释得通，但没有一版改在真正的原因上。

同一件事的两个尺度，难度完全不同。这一章讲这条分界线：为什么代码是模型最早落地的领域，以及为什么“会写函数”和“能改一个仓库”之间隔着一整个工程。

### 为什么是代码

有五个原因，每一个都很实在。

第一，语料多。开源仓库上亿个，代码问答站几千万条，官方文档里有大量示例。代码是互联网上最规整、最密集的逻辑文本。

第二，对错可判。写完一段代码，编译器告诉你语法对不对，测试告诉你行为对不对，运行告诉你结果对不对。这三道关都是免费的、确定性的、不需要人来判断的。

第三，结构强。括号必须配对，变量必须先定义，函数调用必须参数匹配。这种强约束让模型更容易学到“什么是对的”，也让错误更容易暴露。

第四，复用性高。写一个排序、写一个 HTTP 请求、写一个正则，这些在语料里重复了百万次，模型几乎不会错。而业务逻辑各不相同，那部分它就容易出问题。

第五，用户愿意试。程序员本来就习惯用工具、看文档、复制粘贴。他们对“可能出错”的容忍度高，只要能验证。这让代码成为最早形成正循环的领域：用的人多，反馈多，改进快。

第三条还有一个不明显的效果：它把“信任问题”变成了“工程问题”。文本生成的对错要人来判，代码的对错机器能判。所以同样的模型能力，在代码上可以放心地自动化，在文案上不行。

### 五个层次

代码能力不是一个数，是分层的。每一层的失败方式都不一样。

第一层是行内补全。你打到一半，它接下去。它看到的是当前文件和光标前后的几十行。这一层最成熟，日常使用频率最高，价值也最直接：省掉查文档和敲样板代码的时间。

第二层是函数级生成。给一段说明，它写一个完整的函数。它需要理解输入输出、边界条件、错误处理。这一层在标准任务上很稳，在业务逻辑上要看说明写得够不够细。

第三层是文件级。给一个需求和一个现有文件，让它改。它要理解这个文件里的约定：命名风格、错误处理方式、日志格式、依赖注入怎么做。这一层开始出现“看起来对但不符合本仓库习惯”的问题。

第四层是仓库级。给一个仓库和一个任务，让它找到该改的地方并改对。它要跨文件追踪调用链、理解模块边界、遵守隐含约定。这一层的成功率取决于任务类型：加一个字段、改一个配置，比较容易；修一个并发 bug、重构一个模块，很难。

第五层是从 issue 到提交。给它一个真实的 bug 报告，它要复现、定位、修改、跑测试、写说明。这是目前评测里最接近真实工作的形态，也是最难的一层：它需要一个能跑起来的环境、一套能判断对错的测试、以及足够的上下文。

### 不只是写

把代码能力只理解成“生成代码”，会漏掉一半的用处。

读代码是其中最被低估的一项。接手一个陌生仓库，让它解释“这个模块负责什么”“这个函数为什么要有那个参数”“这段代码在什么情况下会走到这里”，比一层层翻调用链快得多。它可能解释得不完全准，但能给你一个起点，而起点是最贵的。

写测试也是。给它一个函数，让它列出该测哪些边界，再让它把测试写出来。它列边界的水平不稳定，有时会漏掉最关键的那条，但它列出来的那些通常值得看一眼，能补上你想不到的情况。

迁移和改写。把一段 Java 翻成 Python，把回调风格改成 async，把旧版本的 API 换成新版本。这类工作机械、量大、容易出错，正适合交给它，然后靠测试兜住。

审查。让它看一段 diff，问“这段改动有没有引入风险”。它的判断不能直接采信，但它常常能指出你没注意的地方：空指针、资源没释放、日志里打印了敏感字段。把它当成一个不会累的第一读者。

文档。从代码生成注释、从接口生成说明、把散落的约定整理成一份 README。这类产出不追求精确到字，追求覆盖到点，模型做得不错。

这些用途有一个共同点：它们的产出都需要人来确认，但确认的成本远低于自己从头做。这也是代码能力真正的价值所在，不是“替你写完”，而是“把起点往前推一大截”。

### 四种典型失败

第一种，编造 API。它会写出一个不存在的函数，比如某个库里没有的方法，或者一个已经被移除的接口。代码读起来毫无破绽，一运行就报错。原因是它在按“这里应该有一个什么形状的调用”采样，而不是在查一个真实的函数表。

第二种，编造包名。它会 `import` 一个不存在的库，名字起得很像真的。这些名字可能真的被人抢注过，装上去就是一次供应链攻击。这类攻击在公开报告里已经出现过多次，成本极低。所以“不要盲目安装模型建议的包”是一条必须写进流程的规矩。

第三种，只处理顺利路径。空文件、非 UTF-8 编码、被截断的日志行、跨零点的时段，这些它不主动想。你问它“有没有边界情况”，它能列出一堆；你不问，它默认输入是干净的。

第四种，版本漂移。它的训练数据里有一个时期的写法，你的环境是另一个版本。同一个库三年内可能改过三次接口，它给你的是它见过最多的那个。

这四种失败都可以用同一套办法压下去：告诉它版本号，把报错原文贴回去，要求它写测试，要求它列出假设。代码任务的好处是，这套办法真的有效，因为验证是机器做的，不依赖你的判断力。

### 仓库级任务难在哪

把“写函数”和“改仓库”放在一起比，差距在四个地方。

一是上下文装不下。一个二十万行的仓库，不可能全塞进窗口。要它定位问题，得先做检索：找出相关文件、相关函数、相关测试。检索做不好，它就在错误的文件里改。

二是依赖关系。改一个函数的签名，可能影响十几个调用点。它看到的是你贴给它的那几个文件，看不到全部调用者。所以它会改得很局部，然后编译失败。

三是隐含约定。这个仓库为什么用这种错误处理方式？为什么这个模块不许直接访问数据库？这些约定往往没有写在文档里，只写在老员工的记忆和代码评审的评论里。模型没有这些信息，它按“通用最佳实践”写，写出来的东西不符合本仓库的习惯。

四是环境。跑测试要装依赖、要起服务、要准备数据。模型看不到这些，它只能猜“测试大概会这么跑”。所以它给的修改常常“逻辑上对，环境上跑不起来”。

这四条里有三条是信息问题，不是智力问题。所以业内的做法不是“等更强的模型”，而是“把信息喂进去”：检索相关代码、把测试跑起来、把评审意见作为反馈、把仓库的规范写进提示。这也解释了为什么同一个模型，在配置好的工具里表现好得多。

### 一个能用的仓库级流程

如果真要在仓库里用它，一个不容易翻车的流程是这样的。

第一步，先让它找，不让它改。给它任务描述和一份文件清单（不是全部代码），让它说“要改哪几个文件、每个文件改什么、为什么”。这一步的产出你审一遍，比审代码快得多。找错了地方，后面全白搭。

第二步，让它读测试。现有测试里往往写着这个模块的约定：什么情况下该抛异常、什么情况下该返回空。它读了测试，就知道该守什么。

第三步，让它写一个能复现问题的测试。这一步是关键。测试跑红了，说明它真的理解了问题；测试一跑就绿，说明它没复现出来，后面改的都不是地方。

第四步，改代码，跑到这个测试变绿。

第五步，跑全量测试。这一步经常被跳过，然后在新版本上线时炸出来：它改的那个函数还有别的调用者，那些调用者没有对应的测试。

这五步里，第三步和第五步是分水岭。跳掉它们，成功率会掉一大截，而且失败的方式很难查。

### 两个真实的坑

**多文件重构。** 一个函数改了参数签名，模型找到了它的定义和三处直调用，改完编译通过，测试全绿，上线后三小时出事。根本没找到的调用在另一个仓库里，用的是反射。这类事故的共同点不是“模型不会改”，而是“它不知道谁在用”。

对此只有一个办法：改之前先生成一份影响面清单。让它先把“这个标识符在仓库里出现过几次、分别是定义、调用、字符串引用还是注释”列出来，你对着清单判断。经不起这个检查的重构，宁可不做。

**代码评审意见。** 另一个高频场景：一个 PR 提上去，收了二十条评审意见，让它改。结果它改了十二条，漏了五条，又顺手动了三处没人提的地方。

问题出在“二十条意见”是一段自然语言，里面混着三类东西：必须改的（安全、错误处理）、建议改的（命名、注释）、以及提问（“这里为什么这么写”）。模型把它们当成一类处理，于是要么全改（把提问也当成修改指令），要么挑着改（漏掉排在后面的）。

工程上的做法是把意见变成清单：每条带上文件、行号、类型（必修/建议/提问）、状态（待改/已改/不改及理由）。改完逐条回填，没改的必须写清楚为什么。这套流程人做很繁，机器做正合适，但它需要你先把那二十条自然语言拆成结构化的一行行。

### 测试是这件事的核心

如果只能给一条建议，那就是：让它写测试，并且真的跑。

原因不只是“测试能发现错误”。更重要的是，测试把一次性的生成变成了一个可以被反复修正的循环：写代码、跑测试、看报错、改代码。模型最擅长的就是根据报错改代码，因为报错是明确的、局部的、有具体信息的。

没有测试，你只能靠读。读代码判断对错，需要的能力比写代码更高，而多数人没有那么多时间。有测试，判断就变成一个机械动作：红了还是绿了。

所以成熟的用法是这样的：先让它写测试（或者你自己写），确认测试能复现问题；再让它改代码，跑到绿；最后让它解释改了什么、有没有引入风险。三步里，第一步最容易被跳过，也最值得坚持。

一个提醒：测试通过不等于正确。测试只覆盖你写的那些情况，而模型的错误往往在你想不到的地方。所以测试要覆盖边界，而边界的清单最好由人来列。

### 对写代码这件事的影响

最后一个问题：它改变了什么。

短期看，它把“写”的成本降下来了，把“读”和“判断”的成本顶上去了。样板代码、胶水代码、文档、测试，这些以前嫌烦的活现在几秒钟就有初稿；但你要花时间读它写的每一行，判断对不对、符不符合规范。

中期看，代码评审的负担会变重。以前评审的是同事写的代码，风格大致可预期；现在评审的可能是模型写的，风格飘忽，还带着“看起来很合理”的错误。有些团队开始要求“AI 生成的代码必须附测试和说明”，这不是形式主义，是为了让评审有抓手。

长期看，能力结构会变。手写快速排序的价值下降了，把需求拆清楚、把边界想全、把系统设计对的价值上升了。这不是“程序员要失业”或者“人人都能编程”这种粗糙结论，而是同一件事的重心在移动：从“敲出来”移到“想清楚”和“验明白”。

::: {.keypoint}
**记住这三件事**

一、代码最先落地，是因为语料多、结构强、而且对错能被编译器和测试判定。

二、它的能力分层：行内补全很稳，函数级看说明，仓库级要跨文件追踪和隐含约定，越往上越依赖信息而不是智力。

三、让它写测试并真的跑，是把“信不信它”变成“红还是绿”的最有效办法。
