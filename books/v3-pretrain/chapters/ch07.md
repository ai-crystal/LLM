## 词表大小的账

两个团队，同样的 8B 骨架、同样 15 万亿 token 的语料、同样一千张卡跑三周。一个把词表定在三万二，另一个定在十二万八。前者的嵌入矩阵 1.3 亿参数，后者 5.25 亿——多出来那 4 亿参数看上去只是零头。可把三项开销摆在一起算，后者在同一份语料上省下约 15% 的训练算力，代价是每个 token 多付 5% 的算力。一整场预训练在这个尺度上是百万美元量级的开支，15% 就是十几万美元，不是一个可以靠手感定的参数。

这道题的三个变量分别是：同一份文本要切成多少 token，嵌入矩阵要占多少参数，每处理一个 token 要做多少次浮点运算。它们的方向不一致——词表越大，第一个数下降，第二个数上升，第三个数先升后降。这一章把三项写成式子，代入具体模型算一遍，再看多语言、代码、数字这些情况把算术推到哪里。

### 一份文本，三种计价方式

先定义压缩率 $r$：一个 token 平均覆盖多少个字符。$r$ 是分词器的属性，给定词表和合并规则就固定了，与模型无关。一段 $S$ 个字符的文本变成

$$D=\frac{S}{r}$$

个 token。$D$ 决定后面所有的账：训练按 token 计费，上下文窗口按 token 计长度，推理按 token 计时间。

$r$ 有实测值。Llama 3 的技术报告给了一组干净对比：同一份英文样本，Llama 2 的三万二词表切出 3.17 字符每 token，Llama 3 的 128256 词表切出 3.94。词表翻两番，压缩率涨 24%。

这个数自己也能测，成本很低：从目标语料里抽几吉字节，用现成分词器工具各训一个三万二、七万、十五万的 BPE，然后在留出的一百兆上跑一遍 `len(text)/len(tokens)`。做法比数值重要——$r$ 不是文本的属性，是“文本配比 × 词表”的属性，代码、中文、表格各测一份，得出的三个数会差出一倍以上。只看英文测出来的压缩率，拿到中文语料上会系统地偏乐观。

24% 听着不多，放进 $D=S/r$ 里就是同一份语料少处理 20% 的 token。训练算力的主项是

$$C\approx 6ND$$

$N$ 是参数量，$D$ 是训练 token 数，系数 6 是每个参数每个 token 的浮点运算次数：前向 2 次（一次乘加），反向 4 次（两次乘加）。$D$ 少 20%，$C$ 就少 20%，这是同一份模型、同一份文本上的直接折扣。

词表本身也要占参数：

$$E=Vd$$

$V$ 是词表大小，$d$ 是隐层宽度，输入嵌入是一张 $V\times d$ 的表，每行一个 token 的向量。这张表不参与 token 之间的任何交互，整个网络里它只做一件事：把整数编号换成向量。输出层如果不与输入共享，再付一份同样的 $Vd$。

把 $E$ 放进算力式时要小心位置。输入侧是查表，一次访存，没有矩阵乘法；输出侧是实打实的矩阵乘，第 $t$ 个位置的隐状态 $h_t\in\mathbb{R}^{d}$ 乘上 $W\in\mathbb{R}^{V\times d}$，得到 $V$ 个 logits。所以算力账上只算输出那份：

$$C\approx 6D\big(N_{\text{ne}}+Vd\big)$$

$N_{\text{ne}}$ 是非嵌入参数（non-embedding parameters），$Vd$ 是输出投影那一项。白话：词表在算力上不是白拿的，每多一个词表项，训练中的每个 token 都要多算一次 $d$ 维内积。

### 嵌入矩阵：一张只查表的参数表

代入数字。Llama 2 的 $V=32000$、$d=4096$，一份嵌入 $32000\times4096=1.31\times10^{8}$，两份 $2.6\times10^{8}$，占 6.7B 的 3.9%。Llama 3 的 8B 把词表加到 128256、$d$ 仍是 4096，一份 $5.25\times10^{8}$，两份 $1.05\times10^{9}$，占 8.03B 的 13%。

13% 值得停一下：每八个参数就有一个躺在两张查表矩阵里，不参与注意力、不参与前馈、不做任何组合。小模型上这个比例会失控。Qwen2-0.5B 的 $V=151646$、$d=896$，一份 $1.36\times10^{8}$，两份 $2.72\times10^{8}$，占 0.49B 的 55%。一半以上的参数用来存词。

| 模型 | V / d | 一份 Vd | 占全模型（共享） |
|---|---|---|---|
| BERT-base | 30522 / 768 | 2.30e7 | 21%（是） |
| Llama 2 7B | 32000 / 4096 | 1.31e8 | 2.0%（否） |
| Llama 3 8B | 128256 / 4096 | 5.25e8 | 6.5%（否） |
| Qwen2-0.5B | 151646 / 896 | 1.36e8 | 28%（是） |
| Qwen2-72B | 151646 / 8192 | 1.24e9 | 1.7%（否） |

表里最后一列的差别留到后面讲。先看清一件事：$Vd$ 的占比不是词表单独决定的，是 $V$ 与 $d$ 的比值决定的。$d$ 大，词表显得便宜；$d$ 小，词表显得贵。0.5B 的 $d=896$，一个 token 的向量只有 896 维，词表却有 15 万个词，存词的开销自然压倒一切。这也解释了为什么小模型的词表往往更小、嵌入往往共享——不是设计者不想支持更多语言，是参数预算撑不住。

还有一笔账不写在参数量里。词表尾部那些 token 在整个语料里出现得少，嵌入拿到的梯度也少。用 Zipf 估一下：若最高频 token 出现 $K$ 次，第 $i$ 名的频次约 $K/i$。一份 15 万亿 token 的语料，$K$ 按 1% 算是 $1.5\times10^{11}$，排到 10 万名的 token 还能出现 150 万次，训练充分。换一份 1000 亿 token 的小语料，$K=10^{9}$，同一位置的 token 只剩一万次，嵌入开始欠训练，模型对它的处理变得不稳定。词表大小必须和语料规模一起看，这是同一个词表在大模型上没问题、在小模型上出问题的原因。

这张表的更新方式也和其他参数不同。一步训练里，只有 batch 中真正出现过的那些 token，对应的行才会拿到非零梯度，其余十几万行原封不动——嵌入是稀疏更新的，而旁边的前馈矩阵每步都在全量更新。这个差别在数据和显存上都有回响：如果设备之间按 $V$ 维切分嵌入，而每个 batch 碰到的 token 分布又不均，某些卡就会空转。

### 压缩率：同一份文本换多少个 token

$r$ 与 $V$ 的关系可以估一个弹性。把三万二到十二万八看作 4 倍，$r$ 从 3.17 到 3.94，比值 1.243。若近似成幂律 $r\propto V^{\gamma}$，取对数：

$$\gamma=\frac{\ln(3.94/3.17)}{\ln 4}=\frac{0.223}{1.386}=0.16$$

白话：词表每翻一倍，压缩率涨约 12%，token 数少约 10%。这个数是从一次跨模型对比里抠出来的，数据配比、预分词正则都变了，只能当量级用。但它和 BPE 的机制吻合：每次合并只作用于当下最高频的相邻对，词表越大，新增的合并在频次曲线上越靠后，收益自然递减。

压缩率的好处不止在训练。上下文窗口按 token 计，窗口 128k 时，$r=3.17$ 能装 40 万字符，$r=3.94$ 能装 50 万。注意力那部分算力按 $T^2$ 涨——每层两个 $T\times T$ 的矩阵乘，约 $4T^{2}d$ 次浮点运算——token 少 20%，这一项降 36%。KV 缓存按 $T$ 线性涨，同样降 20%。

给一个具体数。Llama 3 8B 每层 8 个 KV 头、头维 128、共 32 层，每个 token 的缓存是 $2\times32\times8\times128=65536$ 个数，bf16 下 128 KiB。12.8 万 token 的上下文要 16 GiB。同一份 50 万字符的文档，三万二词表下切出 15.8 万 token，缓存 19 GiB，还超窗；十二万八词表下是 12.7 万 token，缓存 15.5 GiB，刚好装得下。同一块显存、同一份文档，词表决定了它能不能一次读完。

压缩率与计费之间还有一层错位。接口按 token 报价，用户付的是 token 数，但要的是字符数或信息量。中文用户在这个换算里天然吃亏：同一份文档，中文切出的 token 数比英文多，单价一样时总价就高出一截。反过来，词表变大使中文的 $r$ 上升，相当于给这部分用户降了一次价，而这次降价不会出现在价目表上。

### 词表把算力花在了哪里

推理时每个 token 的前向是 $2(N_{\text{ne}}+Vd)$ 次浮点运算。Llama 3 8B 的输出层是 $2\times128256\times4096=1.05\times10^{9}$，整个前向约 $2\times7.51\times10^{9}=1.5\times10^{10}$，占 7%。这部分与上下文长度无关，短请求上尤其显眼：一个只有十个 token 的请求，也要把 12.8 万个 logits 全算一遍。反过来看，这批参数在显存里也是整块占着：bf16 下两份 $1.05\times10^{9}$ 参数要 2.1 GB，与 32 层注意力的权重加起来只能算零头，但它对访存带宽的消耗是每 token 必付的——查表本身不费算力，费的是把那一行从显存搬到片上。

把两种词表放在同一份文本上对比，账就清楚了。取 $S=4.76\times10^{13}$ 字符（三万二词表下正好 15 万亿 token），非嵌入参数 $N_{\text{ne}}=6.98\times10^{9}$，$d=4096$：

| | 三万二词表 | 十二万八词表 |
|---|---|---|
| 压缩率（英文字符每 token） | 3.17 | 3.94 |
| 同一份文本的 token 数 | $1.50\times10^{13}$ | $1.21\times10^{13}$ |
| 一份嵌入 / 两份 | $1.31\times10^{8}$ / $2.62\times10^{8}$ | $5.25\times10^{8}$ / $1.05\times10^{9}$ |
| 每 token 前向浮点运算 | $1.42\times10^{10}$ | $1.50\times10^{10}$ |
| 预训练总浮点运算 | $6.4\times10^{23}$ | $5.4\times10^{23}$ |

表里最后一行相差 15%，是三种效应叠出来的：token 少 20%（省），每 token 多算 5.6%（付），参数多 4 亿（付）。多出来的 96256 个词表项在整场训练里各付

$$6\,d\,D=6\times4096\times1.21\times10^{13}=2.97\times10^{17}$$

次浮点运算，合计 $2.9\times10^{22}$，占十二万八方案总预算的 5% 上下。白话：每多一个词表项，相当于把“所有训练 token 都过一遍这个 $d$ 维内积”的价格乘上一个，积少成多；但它换回来的 token 折扣比这笔支出大，净账是赚的。

要是模型只有 1B、$d=2048$，多出来的词表项在总参数里占比更大（一份 2.6 亿，占 1B 的 26%），那 5% 会膨胀到十几个点，净收益被吃掉大半。同一个词表选择在大模型上划算、在小模型上不划算，原因是参数占比，不是压缩率。

那为什么不干脆加到 50 万？先把这个问题写成一个最优化。把 $D=S/r$ 与 $r\propto V^{0.16}$ 代入训练成本，去掉与 $V$ 无关的常数，要最小化的是

$$\frac{N_{\text{ne}}+Vd}{V^{0.16}}$$

对 $V$ 求导置零：$V^{-0.16}d=0.16V^{-1.16}(N_{\text{ne}}+Vd)$，两边乘 $V^{1.16}$ 得 $0.16(N_{\text{ne}}+Vd)=Vd$，也就是

$$Vd=\frac{0.16}{0.84}N_{\text{ne}}\approx0.19\,N_{\text{ne}}$$

白话：最优点落在“嵌入参数等于非嵌入参数的两成”附近。8B 模型对应 $Vd=1.5\times10^{9}$，$d=4096$ 时 $V\approx3.7\times10^{5}$：37 万词表。这个数比实践中流行的大得多，差距本身就是信息。弹性 0.16 只在三万到十三万这一段测过，外推到 50 万未必成立；而且这个目标函数里没有“尾部 token 训不够”“softmax 分母变大”“词表在张量并行里要切一份通信”这些项。把 37 万当上界，把实践中的 10 万到 20 万当折中，两者相差的那一段就是这些被忽略的项在收费。

### 多语言与代码：稀释与切分

BPE 的合并按整个语料的频次做，配比即命运。九成英文的语料，前十万次合并几乎全部落在英文片段上，其他语言只能分到零头。后果直接写在 $r$ 上：《Language Model Tokenizers Introduce Unfairness Between Languages》(2023) 测了同一段内容在多种语言下的 token 数，缅甸语、掸语这类低资源语言要花 7 到 15 倍于英语的 token。

中文介于中间。以英文为主的三万二词表下，一个汉字常要 1 到 2 个 token：常用字多半能整体进表，生僻字退回 UTF-8 的三片字节。把中文按比例放进分词器训练、词表扩到 15 万，常见双字词整块进表，$r$ 从 1.5 上下抬到 2 以上——这个数随语料配比浮动很大，只能当量级。

把这件事换算成钱，会看到一个不太公平的结构。同样的训练算力，英文文本能看一单位，缅甸语只能看七分之一；同样的上下文窗口，英文能装 12 万 token 的内容，缅甸语装 1 万 token 的等价信息。训练成本、推理成本、有效上下文三道门同时收一次“语言税”，而税率的决定者只是分词器训练时那份语料配比。贵只是表面，更深的一层是：序列变长意味着同样的窗口装的信息变少，模型在这些语言上的有效容量被词表压掉一截，这部分损失不会体现在英文 benchmark 上，于是很容易被当成“模型本来就不擅长这种语言”。

修补的办法在分词器训练那一步：把低资源语言的样本在上采样后重复几遍再跑 BPE，让它们的相邻对能挤进合并序列的前面。代价是英文的合并次数被挤掉一些，英文 $r$ 会略微变差。这是一个零和的预算分配，不是一项可以两边都讨好的优化。分词器训练完之后，这个配比就固定了，后面再给那种语言补多少数据，都不会改变它的切分方式。

代码有自己的规律。缩进用的连续空格在词表里通常有专门的一两个 token（四个空格一个 token 是常见切法），缩进深度于是变成一两个符号，模型对缩进很敏感，也容易在深层嵌套里数错层。数字的处理更微妙：把 `1234` 整块收进词表，`1234` 与 `1235` 就是两个无关的向量，模型没有任何线索知道它们只差一；Llama 2 把数字全拆成单个数字，Llama 3 换成 tiktoken 后按最多三位一组切，前者位数表示稳定但序列长，后者短但跨组进位仍要靠学。

还有一类失效来自分词器与语料的错位：某个字符串在分词器训练数据里高频、进了词表，在模型的实际训练语料里几乎不出现，它的嵌入就停在初始化附近。这类 token 会让模型输出无法预测的内容，社区里以 SolidGoldMagikarp 出名。DeepSeek-V3 遇到过同一类问题的温和版本：新分词器加入了“标点加换行”的合并 token，在多行提示末尾没有换行的场景下产生了 token 边界偏差，他们的补法是训练时随机拆开一部分这类合并 token。

### 三万二到十二万八：一次真实的迁移

Llama 3 的做法是把词表分两半拼起来：十万个 token 来自 tiktoken，另外 2.8 万个专门为非英语挑选。技术报告给的结果是英文压缩率从 3.17 到 3.94，非英语提升更大，且新增 token 对英文分词没有影响。Qwen2 的词表是 151646 个常规 token 加 3 个控制符，对外报 151936——补齐到 128 的倍数，因为张量并行要沿 $V$ 维切分，GPU 上的对齐也要求整块。GLM-4 走的是另一条路：直接在 cl100k_base 上合并中文与多语言 token，凑成 15 万词表，配 10 万亿 token 预训练。

换词表不是免费的。旧 checkpoint 里嵌入矩阵的每一行对应一个具体 token，词表一变，行与 token 的对应关系就断了。实践中的做法是重建嵌入矩阵——新 token 若由旧 token 拼成，就用那几片旧嵌入的均值初始化——然后用小学习率在几百亿 token 上“换血”。共享输出层时更麻烦：改的是同一张表，读写两侧同时被扰动，换血期出现损失尖峰几乎免不了。这意味着词表一旦定下，中途改的代价是补训一段，而补训的那段数据和原来的配方对不上。

词表大小还有几个工程上的副作用。第一，输出层按 $V$ 维切分是张量并行里最自然的一刀：$V$ 越大，切得越均匀，单卡上的 logits 越少，但 all-reduce 的通信量也随之变大。第二，softmax 要在一整个 $V$ 维向量上做归一化，$V$ 大时这一步在长序列上会变成不可忽视的开销，FlashAttention 那类技巧帮不上忙。第三，词表大小通常要凑成 128 或 256 的整数倍，否则切分与对齐都要额外处理——这是 Qwen2 那两个数字 151646 与 151936 之间差的来源。第四，新增的特殊 token（对话角色、工具调用的起止、图像占位）挤在词表尾部，它们的嵌入要从零学起，给几个、放在哪，也会影响首批训练步的稳定性。这些项单独看都只有百分之几，加起来正是上界与实践之间那段距离。

### 输出层共享：一份还是两份

输出层要不要和输入共用同一张表，是一道单独的题。不共享时，logits 是

$$z_t=W h_t,\qquad W\in\mathbb{R}^{V\times d}$$

共享时把 $W$ 换成嵌入矩阵 $E$，第 $v$ 个 logit 变成 $z_{t,v}=\langle h_t,e_v\rangle$，即当前隐状态与第 $v$ 个 token 嵌入的内积。白话：输出层在问“这个位置的隐状态和哪个词的向量最像”，而输入层用同一套向量表示“这个词长什么样”，读写被强制共用一套坐标。

省参数是最直接的好处。Qwen2-0.5B 共享之后，存词的开销从 55% 降到 28%，等于凭空多出 1.36 亿参数给真正的计算。第二个好处是梯度：共享的每一行既作为输入被读到、又作为目标被预测到，同一个 token 拿到两份信号，长尾词的嵌入训练得更充分，这在小语料上效果明显。第三个是正则——把读写绑在一起，等于给嵌入加了一个约束，实践中能压低过拟合。

梯度那一条可以写细一点。共享时，嵌入第 $v$ 行的总梯度是两项之和：

$$\frac{\partial \mathcal{L}}{\partial e_v}=\underbrace{\sum_{t:\,x_t=v}\frac{\partial \mathcal{L}}{\partial h_t}}_{\text{它作为输入出现时}}+\underbrace{\sum_{t:\,y_t=v}\frac{\partial \mathcal{L}}{\partial z_{t,v}}h_t}_{\text{它作为目标出现时}}$$

$x_t$ 是位置 $t$ 的输入 token，$y_t$ 是那个位置要预测的标签。白话：一个词既在句子里被读到，又在别处被当成要预测的答案，两条路径都会往它那一行里灌梯度。对于一个高频词，这两项都很强；对于一个低频词，第二项往往是它唯一的强信号——因为它作为目标出现时，总是伴随一个明确的“这里该出它”的位置。

代价是自由度。输入需要的是“区分语义”，输出需要的是“区分频次与表面形式”，这两件事的最优几何并不相同。$d$ 大时，省下的 $Vd$ 相对全模型不值钱（72B 上一份只占 1.7%），解耦多出来的自由度就更值钱。Qwen2 的选择把这条界线画得很清楚：0.5B 与 1.5B 共享，7B 与 72B 不共享。

还有第三种做法，ALBERT 用过：把嵌入分解成 $V\times E$ 与 $E\times d$ 两个小矩阵，$E\ll d$。$V=30522$、$E=128$、$d=768$ 时参数量是 $3.91\times10^{6}+9.8\times10^{4}\approx4.0\times10^{6}$，比一张 $Vd=2.3\times10^{7}$ 省近六倍。代价是词向量先被压到 128 维再投影，表达被掐了一道，后面要靠更多层补回来。

### 给中文加两万个位置值不值

这个题有确定的算法，不靠手感。设中文占语料 5%，即 $7.5\times10^{11}$ 个 token；当前分词器的中文压缩率 $r=1.4$ 字符/token；扩两万个中文 token 后 $r$ 抬到 2.0（实测过双语词表的值就在这个区间）。

先算省下的 token。同一批中文原文，字符数不变，token 数按 $r$ 反比缩：

$$\Delta D=7.5\times10^{11}\times\left(1-\frac{1.4}{2.0}\right)=2.25\times10^{11}$$

再算每 token 的算力。8B、$d=4096$、$N_{\text{ne}}=6.98\times10^{9}$，扩表前的输出层是 $Vd=5.25\times10^{8}$：

$$6\left(N_{\text{ne}}+Vd\right)=6\times7.5\times10^{9}=4.5\times10^{10}$$

省下的总量是 $4.5\times10^{10}\times2.25\times10^{11}=1.0\times10^{22}$ FLOPs，占总预算 $6.4\times10^{23}$ 的 1.6%。

代价那一头：多出的两万个 token 每个都要在**全部**训练 token 上过一次内积，不是只在中文上：

$$6\times4096\times2\times10^{4}\times1.5\times10^{13}=7.4\times10^{21}$$

（比 1.6% 少一半，因为中文只占 5%。）净收益 $2.6\times10^{21}$，约占总预算的 0.4%。

0.4% 看不出是赚了。把两式对消，解出盈亏平衡点：

$$s^{*}=\frac{d\,\Delta V}{(r_1/r_2-1)\left(N_{\text{ne}}+Vd\right)}=\frac{8.2\times10^{7}}{0.3\times7.5\times10^{9}}=3.6\%$$

中文占比超过 3.6%，扩表就是赚的。这个门槛低得意外，原因是必付的代价（两万个内积）随 $d$ 线性涨，而收益随“中文占比乘压缩率增益”线性涨，后者在 5% 时已经占优。

但预训练那 0.4% 只是一部分。推理上同一段中文的 token 数少 30%，而这 30% 是每一次请求都要付的。服务一百万用户时，这笔折扣比预训练那点算力大得多。所以扩表的真正理由不是“训得更便宜”，是“每个 token 装更多中文”。

反过来的情况也真存在。一个只做英文、服务量小、模型只有 1B 的团队，扩表只会把 26% 的参数花在存词上，而那两万个中文 token 在它的语料里一次也不出现——上面公式里 $s=0$，左边收益为零，右边代价照付。

### 死 token：词表里那几万行从不出现

分词器在一份语料上训出来，模型在另一份语料上训练。两份语料不一样，就会有一批 token 从没被用过。

它们从哪来。分词器训练用的是清洗前的抽样——两千万句里混着 PDF 抽取的乱码、私用区字符、各种 emoji、被截断的 URL。这些片段在清洗后大多消失了，但它们当初是高频的，于是理所当然地进了词表。实测上，十五万词表里百分之五到十的行在整个训练中一次也不出现，也就是七千到一万五千行。

这些行有两个后果。一是显存：七万二千亿参数、$d=8192$、一万两千份死 token，每份参数是 $1.2\times10^{4}\times8192\approx10^{8}$，bf16 下两百万份（输入输出各一份）是 0.4 GB。不大，但白占着。

二是 softmax 的分母。这些行的梯度恒为零，权重衰减会把它们压向 0，logit 也就是 0，对应 $\exp(0)=1$ 这一项永远留在分母里。若分母的其余部分总和为 $Z_{\text{live}}$，则损失被抬高

$$\Delta\mathcal{L}=\ln\!\left(1+\frac{1.2\times10^{4}}{Z_{\text{live}}}\right)$$

$Z_{\text{live}}$ 在训练早期很小（logits 都接近 0，约等于活 token 数 14 万），这一项可忽略；而到后期模型很自信时，$Z_{\text{live}}$ 主要由少数高概率 token 撑起，可能只有几万，这时死 token 能把损失抬高 0.1 nats 量级。这个抬升是真损失还是度量偏差有争议，但它确实占用了概率质量——模型把百分之几的“预算”分给了永远不会出现的词。

处理办法有两个。一是在分词器训练前把语料清洗干净，让词表里根本不出现乱码 token；二是训完分词器后，在真实训练语料上统计一遍 token 频次，把频次为 0 的项标出来，训练时在 softmax 里遮掉。后者的代价是一份掩码，好处是能直接看到“词表浪费了多少”。

检查这件事只要三行：

```python
from collections import Counter
cnt = Counter(t for doc in corpus for t in tok.encode(doc))
print(len(cnt) / tok.get_piece_size())
```

分母是词表大小，分子是真正用到的不同 token 数。低于 0.9 就该回头看分词器的训练语料了。

### 输出层的账单：$V$ 大在哪里最贵

参数占比只是一面，另一面是每步要付的钱。输出层是模型里唯一一个“每个 token 都要碰全部 $V$ 行”的地方，而它的代价分两种。

第一种是算力。每个 token 的输出投影是 $2Vd$ 次浮点运算，与上下文长度无关：

| 词表 | 每 token 输出层 FLOPs | 占 8B 前向比例 |
|---|---|---|
| 32 000 | $2.7\times10^{8}$ | 1.8% |
| 128 000 | $1.05\times10^{9}$ | 7.0% |
| 256 000 | $2.1\times10^{9}$ | 14.0% |

十四。词表再大一倍，光输出层就吃掉七分之一的算力，而它只干一件事：把隐状态变成一个分布。

第二种是带宽，而在解码阶段它比算力重要得多。自回归解码时，一个 token 的前向要把全部权重从显存读一遍：8B 模型 bf16 是 16 GB，HBM 带宽按 3 TB/s 算是 5.3 毫秒，对应 190 token/s 的单序列速度。输出层在其中占 1.05 GB，也就是 0.35 毫秒、6.6%——与算力占比碰巧接近，因为两者都只跟 $Vd$ 有关。

真正拉开差距的是批。批大小从 1 加到 32，算力需求乘 32，带宽需求几乎不变（权重只读一次，被 32 个序列共用）。于是解码从“带宽受限”变成“算力受限”，输出层那一项的占比从 6.6% 跳到 7% 以上的算力占比。也就是说，高并发服务下，大词表的代价从“每 token 多搬 1 GB”变成“每 token 多算 1e9 次”。前者靠堆带宽缓解，后者只能堆卡。

还有一个隐藏成本：softmax 要在整个 $V$ 维向量上做归一化。$V=128000$ 时，一个位置上要算 12.8 万次指数与加法；批 32、序列 4096 的一次 prefill 就是 $1.7\times10^{10}$ 次指数运算。指数运算在 GPU 上是特殊函数单元（SFU）干的，吞吐只有普通乘加的十六分之一。所以大词表不只是多了一次矩阵乘，还多了一次全词表的 exp——这一项在长 prompt 的 prefill 里能占到几个百分点，而 FlashAttention 那类优化帮不上忙，因为它优化的是注意力，不是投影。

把这些放在一起，就能解释一个常见的工程选择：词表大到一定程度后，输出层单独切出来放在专门的卡上（词表并行），或者改用分层 softmax、采样近似。这些技巧都不在预训练的主流配置里，因为预训练时算力花在 $6ND$ 上，输出层那点占比不到一成；而推理时每一个 token 都要重复付这笔钱，账就反过来了。

### 同一个模型，两种词表：一次可以自己做的测量

词表决策里唯一不能拍脑袋的数就是压缩率。它只能测，而且测起来很便宜。

做法：从最终语料里按配比抽 2 GB（英文网页 45%、中文 25%、代码 20%、数学 10%），用两个候选分词器分别编码，按域统计字节数除以 token 数：

| 域 | 32K 词表 | 100K 词表 | 提升 |
|---|---|---|---|
| 英文网页 | 4.05 | 4.42 | 9% |
| 中文网页 | 2.10 | 3.05 | 45% |
| 代码 | 3.30 | 3.52 | 7% |
| 数学 | 3.60 | 3.80 | 6% |

中英文的差距不是巧合：英文在三万词表里已经拿到了大部分常用词，扩表只能拿到长尾；中文在三万词表里几乎全靠单字和双字片段拼，扩表直接拿到常用词与成语。

把这些数按占比加权，得到整份语料的压缩率：32K 是 3.44，100K 是 4.02，提升 17%。也就是说同一份 340B token 的预算，换词表后能多读 17% 的字。

再把两头加起来算总账。参数上，$d=2048$ 时两份嵌入分别是 $6.6\times10^{7}$ 与 $2.0\times10^{8}$，差 1.34 亿，占 13 亿的 10%；算力上，每 token 输出层从 $1.3\times10^{8}$ 涨到 $4.1\times10^{8}$，而总前向是 $2\times1.27\times10^{9}=2.5\times10^{9}$，占比从 5% 升到 16%。而同样的文本量下 token 数少 14%，训练总算力：

$$\frac{6\times1.4\times10^{9}\times2.9\times10^{11}}{6\times1.27\times10^{9}\times3.4\times10^{11}}=0.94$$

只便宜 6%。这个结果与第七章的结论一致：词表从小扩到中等，收益最大；再往大扩，每多一万个位置换回的压缩率越来越少，而参数与输出层的开销线性涨。对一个以中文为重要目标的小模型，100K 值；对纯英文模型，32K 到 64K 就饱和了。

还有一项不入算力账但入运维账的：词表大了，tokenizer 文件大、加载慢、特殊 token 多、与下游工具的兼容面变宽。这些不是硬成本，但每一次对接都要多查一遍。

### 每多一种语言要多少位置

多语言词表的预算分配有个可以估的起点。一种语言需要多少 token，取决于它的文字系统与语料量，而不是取决于它“重要”。

先看字符集。拉丁字母语言用同一套基本字符，多一种语言的边际成本主要是词级片段；西里尔、希腊、阿拉伯、希伯来各有自己的字符区，需要先付一笔“字符入场费”；中文、日文的汉字集大，入场费最高，但一旦付了，常用词的压缩率提升也最大。

按覆盖 95% 文本为目标，大致如下（量级估计，具体随语料浮动）：

| 语言 | 字符区 | 推荐配额 | 达到的 $r$ |
|---|---|---|---|
| 英文 | 拉丁 | 3 万 | 4.4 |
| 中文 | 汉字 | 2 万 | 2.6 |
| 日文 | 汉字 + 假名 | 1.5 万 | 2.2 |
| 俄文 | 西里尔 | 1 万 | 3.4 |
| 阿拉伯文 | 阿拉伯 | 1 万 | 3.0 |
| 越南文 | 拉丁扩展 | 8 千 | 3.6 |

“达到的 $r$”是按该语言自己的文本算的字符/token，不是与英文对比的相对值。共享一个词表时，这些配额要从同一个总数里分，而总数又被嵌入参数卡着：十二万词表已经是小模型的上限。于是“支持 20 种语言”就变成一个减法题：英文从 3 万压到 2.4 万，中文从 2 万压到 1.5 万，剩下十几万位置按语料占比分。

减法总会疼，而疼的位置可以算。英文词表从 3 万削到 2.4 万，压缩率从 4.4 掉到 4.25（约 3%），而中文从 2 万削到 1.5 万，压缩率从 2.6 掉到 2.2（15%）。同样的削减比例，中文的损失大五倍——因为中文的词表项更“值钱”，每一个覆盖的文本更多。这也是多语言词表里反复出现的结论：不要按语言数量均分，要按“每去掉一万个位置损失多少压缩率”来分。

### 换词表的施工顺序

假设已经决定从 32K 换到 128K，而且模型还没开始训（这是唯一便宜的时点）。施工顺序如下。

第一步，用最终语料重新训分词器，而不是在旧词表上追加。追加的词表能保留旧 token 的 id，但新老 token 的合并顺序不一致，同一个词会被切成两种样子，而这会让旧数据的 token 数组全部作废。重训的代价是几小时，收益是整份词表内部一致。

第二步，用同一份抽样把新旧两个分词器的压缩率、利用率、主切法占比各测一遍，确认新词表真的值那份参数。如果中文压缩率提升不到 20%，而且中文占比低于 5%，那就不要换。

第三步，重写所有 token 数组。340B token 的语料重 encode 一遍，单核每秒约百万 token，并行到几百核是几小时；磁盘上要同时放得下两份（本案例里是 680GB 变 500GB）。这一步没有捷径，因为它必须全部重来。

第四步，重新对一遍特殊 token。旧词表里的 `<|endoftext|>`、对话分隔符在新词表里的 id 会变，所有下游脚本（数据打包、评测、推理服务）都要同步。一个漏改的脚本会把填充符当成正文，而这种错在损失上只表现为“轻微偏高”。

第五步，把新旧词表各自的基准损失对齐。同一份验证集，用旧词表算是 2.03 nat/token，新词表可能是 2.35，这并不代表变差——必须换算到 bit/字节再比。这一步的意义是给后面的训练定一个正确的起点与目标值，否则“损失降到 2.1 以下”这类目标会变成无法判定的空话。

五步加起来两三天，成本主要是人而不是机器。而如果模型已经训完再换，代价就是重训一遍——这也是为什么词表被归入“必须一次做对”的那几个决定。

### 定词表的顺序

把这一章的式子排成一个可执行的顺序，大致是这样：先定语言与领域配比，因为它决定 BPE 的合并落在哪里，也决定 $r$；再在目标语料上采样一百来兆，训三个不同大小的分词器（BPE 训练本身在单机上几分钟到几十分钟），量出各自的字符每 token；然后用 $Vd$ 除以全模型参数，把占比卡在一成以内，小模型直接按共享处理；接着用 $C\approx6D(N_{\text{ne}}+Vd)$ 算总账，选让 $D(N_{\text{ne}}+Vd)$ 最小的那个 $V$；收尾时把它补齐到 128 的倍数，并给对话模板、工具调用、填充这些特殊符号留出上千个位置。

前三步的判断可以归结成两个向反方向拉的量。词表变大，$D$ 按 $V^{-0.16}$ 降，这一项降得慢；$N_{\text{ne}}+Vd$ 按 $V$ 升，这一项升得快。两者相乘是一条先降后升的曲线，最低点就是上面算过的 $Vd\approx0.19N_{\text{ne}}$。参数一换，最优点立刻跟着走：模型从 8B 长到 70B，$N_{\text{ne}}$ 大了一个数量级，最优点对应的 $V$ 也大一个数量级（假设 $d$ 同步变大，则 $V$ 只需大几倍）。这解释了一个看上去奇怪的现象——同一个词表，放在 70B 上是浪费，放在 1B 上又太贵。

收尾那一步是别把词表当可调参数。它一旦定下，分词器、嵌入矩阵、以及所有已经处理过的数据就绑在一起了，后面任何一次改动都是重训一段。换个角度看，$V$ 是整条流水线上少数几个“必须一次做对”的决定，其余大部分参数都可以在训练中调。

回到开头那两个团队：8B、$d=4096$、15 万亿 token 的语料，十二万八词表在同一条数据上省约 15% 的训练算力，推理按字符算也便宜约 15%，只是每 token 的前向贵 5%。服务量大、请求短、语料以英文为主时，这笔账几乎总是站在大词表这边，多出的那 4 亿参数占的显存在推理时也换得回来；服务量小、模型小、语料以某一种非英语语言为主时，词表该往回收，把参数留给计算。

词表定完，参数与 token 的比例也跟着露头了：$Vd$ 一改，$N$ 就变，而“给定算力该训多大模型、喂多少 token”这个问题本身还没有答案。按行业习惯，它有一个很具体的经验值——每参数 20 个 token。这个数字不是拍出来的，它从两条幂律的交点推出来，背后的推导、修正和它什么时候不再成立，是下一章的事。
