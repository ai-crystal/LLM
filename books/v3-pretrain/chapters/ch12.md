## 从零训一个小模型：一份可执行的配方

前面十一章拆开的都是零件：数据怎么洗、词表怎么定、规模怎么算、系统怎么切、训练怎么崩。零件齐了之后，真正动手时的第一个问题反而很朴素——手上只有八张卡和两周时间，能训出什么？

这个问题有确定的答案，而且可以算出来。八张 H100、两周、按 40% 的模型浮点利用率，算力预算是 $8\times990\times10^{12}\times0.4\times14\times86400\approx3.8\times10^{21}$ FLOPs。训练总算力是 $6ND$，$N$ 是参数量、$D$ 是 token 数。给定这个预算，$(N,D)$ 有无穷多种搭配，选哪一种取决于你要它干什么。

这一章把一次完整的预训练拆成八个环节：定目标、定词表、定数据、定模型与超参、过三道启动门槛、排评测与检查点、定排查顺序、算账。每一步都给具体数字和一个 1.3B 模型的算例，照着改参数就能跑。

### 目标先写成一个数

"训一个好用的中文小模型"不是目标，因为无法判断有没有达成。可执行的目标长这样：在 3400 亿 token 上训练一个 13 亿参数的模型，验证集损失降到 2.35 以下，中文常识问答的四选一准确率超过 42%，全部在 14 天内完成。

四个数分别对应四件事：$N$、$D$、损失目标、下游指标。它们之间不是独立的，缩放定律给出了换算关系。把 $D=20N$ 代进 $6ND$，得 $C=120N^2$，于是

$$N_{\text{opt}}=\sqrt{\frac{C}{120}},\qquad D_{\text{opt}}=20N_{\text{opt}}$$

白话：预算固定时，参数量按预算的平方根增长，数据量按同样比例跟上。代入 $C=3.8\times10^{21}$，得 $N=5.6$B、$D=113$B。这是一个"训练最优"的配置——同样的算力下，它的最终损失最低。

但这个答案对你的场景多半是错的。小模型不是用来刷预训练损失的，是要拿去服务的。推理成本正比于参数量，而训练成本正比于 $ND$：把参数减半、数据加倍，训练成本不变（$6ND$ 里 $N$ 减半、$D$ 加倍），推理成本减半。这就是"过度训练"（over-training）的动机，Llama 系列把每个参数配到上百个 token，远超 Chinchilla 的 20。

取 $D=270N$ 量级，$C=6\times270N^2=1620N^2$，得 $N=\sqrt{3.8\times10^{21}/1620}=1.5$B。取整到 1.3B 参数、340B token：$C=6\times1.3\times10^9\times3.4\times10^{11}=2.65\times10^{21}$，占预算的 70%，剩下的 30% 留给消融实验、失败重跑和评测。每个参数 260 个 token，是 Chinchilla 的 13 倍。

| 方案 | $N$ | $D$ | $D/N$ | 训练算力 | 8 卡耗时 | 定位 |
|---|---|---|---|---|---|---|
| 训练最优 | 5.6B | 113B | 20 | $3.8\times10^{21}$ | 14 天 | 研究、比损失 |
| 本配方 | 1.3B | 340B | 260 | $2.65\times10^{21}$ | 9.7 天 | 服务、要便宜 |

计划里必须留出余量，这一点常被低估。9.7 天是从"零故障、满效率"算出来的；实际会掉到 80%–90%（检查点写入、尖峰回滚、节点故障），于是 11 天左右，仍在两周内。如果把预算用到 95%，任何一次事故都会让你延期。

同一套式子可以反算任何预算。四张卡跑一周：$4\times3.96\times10^{14}\times6.05\times10^5=9.6\times10^{20}$ FLOPs，按 $D=260N$ 得 $N=\sqrt{9.6\times10^{20}/1620}=7.7\times10^8$，也就是 7.7 亿参数、2000 亿 token。这个规模的模型在单卡上能直接推理（权重 1.5GB），适合做垂类微调的底座。预算降一个数量级，参数量只降一半——这是平方根关系的另一面：小预算不一定只能做小事，但一定要把每个 token 用在有效数据上。

### 词表：先定分词器

分词器要在模型之前定，因为它决定了三件事：嵌入表多大、同样一段文本要多少 token、以及模型看到的中文是什么样子。

词表大小 $V$ 与嵌入参数的关系是 $V\times d$。$d=2048$、$V=32000$ 时是 6600 万参数，占 13 亿的 5%；$V=128000$ 时是 2.6 亿，占 20%。后者意味着五分之一的参数花在"记住每个 token 长什么样"上，而这些参数在小模型里本来就不该占这么大比重。

反方向是压缩率。同样一段中文，32K 词表可能要 1.5 个 token 一个字，128K 词表只要 1.0 个。压缩率差 1.5 倍，意味着同样的训练预算下模型实际读到的字数差 1.5 倍——这个影响比嵌入参数大得多。

所以词表大小是在两件事之间换：每个 token 的信息量，和每个 token 的成本。量化的办法是直接测。取 100MB 混合语料（按你的最终配比抽），用候选分词器编码，统计

$$\text{压缩率}=\frac{\text{字节数}}{\text{token 数}}$$

英文文本上，32K 词表大约 3.8–4.2 字节/token，128K 能到 4.5；中文（UTF-8 下 3 字节/字）在 32K 上约 2.0 字节/token，也就是一个字 1.5 个 token，128K 能到 2.9 字节/token 上下。把这些数字乘以各语种占比，算出加权平均，再对比嵌入参数的比例，就能定下来。

算例的取法是 32K：中文占 20%、其余以英文为主时，加权压缩率约 3.6 字节/token，340B token 的语料对应 1.2 万亿字节，与真实可获取的中文加英文高质量文本量级相符。100K 以上的词表留给多语言需求更强的模型——每多一种语言，压缩率的收益才能摊薄嵌入表的成本。

分词器自己的训练数据量不必很大。BPE 的合并表在 10GB 量级的混合文本上训就基本饱和，加到 100GB 带来的压缩率改善不到 2%。真正需要调的是两个先验：预分词规则（中文按字还是按词切、数字是否逐位切）和词表里的语种配额。词表大小对每步计算几乎没有影响——嵌入层的参数量是 $Vd$，但它的计算量只占 $2Vd$ 对比整体的 $12Ld^2$，$L=24$ 时不到 1%。所以词表的选择该按"压缩率与嵌入参数"算，不必担心它拖慢训练。

还有三个细节要在训练前定死。词表大小取 128 的整数倍，否则张量并行切词表会切不匀（词表投影按列切，$V$ 不能被整除时最后一张卡会多出一块）。特殊 token 只留必要的几个：结束符、填充、以及一到两个对话分隔符；每加一个都占一行嵌入，且这一行只被极少样本更新，容易成为尖峰来源。数字要不要单独切分，取决于你的目标里有没有算术——把 0 到 999 各作为一个 token，能让算术题的数字表示更规整，代价是词表多一千行。

分词器还有一个容易被忽略的约束：训练用的分词器必须与推理时一致。换分词器等于换模型，微调也救不回来。所以分词器一旦定下，把它连模型一起版本化，写进配置里。

### 数据：配比、剂量与打包

340B token 从哪来。开源的网页语料（经过清洗的 Common Crawl 派生集）、代码、数学题解、中文网页与书籍、学术论文，这五类基本能覆盖一个小模型的需求。配比不是拍脑袋，但也不该一开始就精调——先用一个合理起点跑 50 亿 token，看分域验证损失，再调。

| 来源 | 占比 | token 数 | 有效 epoch | 主要作用 |
|---|---|---|---|---|
| 英文网页 | 45% | 153B | 1.0 | 通用语言能力 |
| 中文网页与书籍 | 20% | 68B | 1.6 | 中文表达与知识 |
| 代码 | 20% | 68B | 0.8 | 结构、推理、格式化输出 |
| 数学 | 8% | 27B | 2.5 | 符号操作、多步推导 |
| 论文与技术文档 | 7% | 24B | 1.2 | 长文、术语 |

"有效 epoch"这一列是关键。同一份数据被看几遍，收益是递减的：第一遍收益最大，第二遍约为一半，第四遍之后基本只剩记忆。数学和代码是例外，它们的样本多样性低但模式密度高，重复两三遍仍有收益。反过来说，任何一类超过 4 个 epoch 都是浪费——不如把那部分算力换成语料清洗，或者干脆接受更小的模型。

配比的技术细节在前面几章讲过，这里只留下三条与配方有关的：去重按段落级而不是文档级（网页转载会把同一段散落在很多文档里）；去污染要按 13-gram 匹配验证集和评测集，命中就删；质量分类器的作用是排序而不是过滤，把分数低的 20% 放到训练的后期（退火阶段），比直接扔掉更划算。

打包（packing）是把变长文档拼成定长序列的过程。序列长度取 2048 时，如果不打包，一个 300 token 的文档要 padding 到 2048，有效计算只剩 15%。打包的做法是把多篇文档首尾相接填满 2048，同时在文档边界处重置注意力（或者至少插入一个结束符），否则模型会学到"上一篇的结尾紧接着下一篇的开头"这种在推理时不存在的模式。

最后一个 5% 的 token 单独处理，叫退火阶段。做法是把学习率从余弦曲线切到更低的一档（峰值的 5%–10%），同时把数据换成质量最高的那部分：精选问答、教材、经过验证的代码。这一段的作用不是学新能力，而是把已有的分布往高质量方向拽。实测上它能把验证损失再压 0.02–0.05，代价是总训练量的 5%。如果预算紧，这一段比多训一成普通数据划算。

token 化的结果要落成二进制数组，每个 token 用 uint16 存（32K 词表刚好够），340B token 是 680GB。训练时按 $(\text{step},\text{rank})$ 算出该读的偏移，直接内存映射读取，不经过任何解析——数据管道一旦成为瓶颈，GPU 利用率会掉到 50% 以下，而排查它要花的时间往往超过省下的存储成本。

### 模型与超参：一份具体配置

13 亿参数怎么摆。按 $N\approx12Ld^2$ 这个常用估算，取 $d=2048$、$L=24$：$12\times24\times2048^2=1.21\times10^9$，加上 32K 词表的嵌入 $6.5\times10^7$，合计 1.27B。

| 项 | 取值 | 理由 |
|---|---|---|
| 层数 $L$ | 24 | $12Ld^2$ 定参数，深宽比约 1:85 |
| 隐维 $d$ | 2048 | 必须能被头数与张量并行度整除 |
| 头数 / 头维 | 16 / 128 | 头维 128 是常规值，QK-Norm 上界 $\sqrt{128}=11.3$ |
| KV 头数 | 8（GQA） | 键值维度压到 1024，省缓存 |
| 前馈隐维 | 5504 | SwiGLU 取 $\frac{2}{3}\times4d$ 再对齐到 128 |
| 序列长度 | 2048 | 与打包粒度一致 |
| 位置编码 | RoPE，$\theta=10^4$ | 2048 长度不需要外推技巧 |
| 归一化 | RMSNorm，Pre-LN | 深层稳定，省一次归约 |
| 词表 | 32000 | 上面算过 |

参数核对：一层是注意力 $4d^2=1.68\times10^7$ 加前馈 $3\times d\times5504=3.38\times10^7$，合计 $5.06\times10^7$，与 $12d^2=5.03\times10^7$ 对得上（差在 5504 与 5461 的取整）。24 层是 1.21B，加嵌入共 1.27B。

超参的起点可以抄，但要知道每一项在管什么。

| 超参 | 取值 | 作用 |
|---|---|---|
| 峰值学习率 | $6\times10^{-4}$ | 13 亿参数、百万 token 批的常用值 |
| warmup | 2000 步 | 占总步数 0.6%，够各层尺度稳定 |
| 衰减 | cosine 到峰值的 10% | 末期低学习率把损失再压一点 |
| 全局批 | 100 万 token | 约 500 条 2048 |
| $\beta_1,\beta_2$ | 0.9, 0.95 | 短记忆，抗尖峰 |
| 权重衰减 | 0.1 | 仅矩阵 |
| 梯度裁剪 | 范数 1.0 | 限单步 |
| z-loss | $10^{-4}$ | 拴住 $\log Z$ |
| 精度 | bf16 乘、fp32 归约 | 范围优先 |

学习率这一项最值得花时间。$6\times10^{-4}$ 是个起点，不是答案：跑三个 50 亿 token 的短实验，学习率分别取 $3\times10^{-4}$、$6\times10^{-4}$、$1.2\times10^{-3}$，看第 50 亿 token 处的验证损失，选最低的那个再微调。三次短实验总共约 10 小时、占用预算 4%，比事后发现学习率不对便宜得多。

批大小有理论依据可查。临界批量（critical batch size）是"再加大批量也不再省步数"的那个点，它随训练推进而增大：训练早期梯度噪声大，临界批量小；后期噪声小，临界批量大。百万 token 的批在这个规模上通常还在临界点以内，判据是做一个批量翻倍的对照——若损失改善不到 10%，说明已经过大，多出来的批量只是在浪费算力。

显存要重新算一遍，因为这一章用的是真实的配置。13 亿参数按 16 字节是 20.3GB；八张卡做 ZeRO-1，每卡 $4\Psi+12\Psi/8=5.1+1.9=7$GB。激活按每 token 每层 40KB（$d=2048$ 时 $20d$ 字节）、24 层算，每 token 约 1MB；全局批 100 万 token 分到八张卡是每卡 12.5 万 token，激活就是 125GB——一张 80GB 的卡装不下。

所以这份配方里必须有激活重计算。前面讲训练系统时推过，全量重算能把激活压到 $2\sqrt{L}/L$ 倍，24 层是 $2\sqrt{24}/24\approx0.41$，即 51GB，加上状态 7GB 与临时缓冲，勉强落在 80GB 内。更稳的做法是配合微批：微批取 8 条序列（1.6 万 token），激活降到 16GB，梯度累积 8 次凑成百万 token 的全局批，此时每步真正算的是 8 次前向加反向。若显存还紧，再加一层选择性重算（只丢注意力矩阵），代价 5% 以内；用全量重算则要多花三分之一的时间，那是把 80GB 卡当 40GB 卡用时才付的价。

步数与单步时间可以从两个式子算出来，它们决定了整个项目的时间表：

$$S=\frac{D}{B},\qquad t_{\text{step}}=\frac{6NB}{F}$$

$B$ 是全局批的 token 数，$F$ 是全部卡合起来的有效算力，$S$ 是总步数。本配方里 $S=3.4\times10^{11}/10^6=34$ 万步，$t_{\text{step}}=6\times1.27\times10^9\times10^6/(3.17\times10^{15})=2.4$ 秒，两者相乘是 9.4 天。注意到 $B$ 在 $S$ 里做除法、在 $t_{\text{step}}$ 里做乘法，所以总时间 $S\cdot t_{\text{step}}=6ND/F$ 与批大小无关——批大只意味着步数少、每步久，不改变总账。批大小真正影响的是收敛（学习率要跟着它调）和显存（激活正比于它）。

### 三道门槛：启动前的检查

历史上最贵的一类事故，是在第三天才发现第一步就错了。下面三道门槛的顺序是有意安排的：越便宜的放越前，越接近真实配置的放越后。

第一道门槛是单批过拟合，花五分钟。取一个微批（8 条 2048 序列），把学习率放大十倍，训练 200 步。交叉熵在初始化时的理论值是 $\ln V=\ln 32000\approx10.4$，如果第一步就显著偏离这个数，说明输出层的初始化偏了；随后 200 步内损失应该降到 0.5 以下，因为它只需要记住这 8 条序列。降不下去的子原因就那么几个：标签与输入错了一位（因果语言模型的标签是输入向右移一格）、损失掩码把不该算的位置算进去了、注意力的遮罩方向反了（能看到未来）、或者优化器没接到某些参数上（常见于手写参数分组时漏了新加的模块）。

第二道门槛是玩具规模的完整跑，花半天。建一个 4 层、$d=512$、约 1300 万参数的模型，在 10 亿 token 上跑一遍，看三件事：GPU 利用率能否稳定在 85% 以上（低了就是数据管道或通信的问题）、损失曲线是否平滑下降（锯齿周期性出现说明数据源切换没打散）、从检查点恢复后损失是否连续（而不是跳一跳）。这个规模算力根本占不满，按算力算 10 亿 token 只要半分钟，实际会慢两个量级：矩阵太小，每步的时间花在读权重和等数据上，实测吞吐每卡两三万 token/s，跑完约一小时。这个“算力用不满”的事实本身就是观察对象——大模型训练追求 MFU，小模型训练追求的是别让数据管道堵住。

第三道门槛是配方对比，花两天。用真实模型、真实数据，只跑 50 亿 token（总剂量的 1.5%），比较候选学习率与两份数据配比。成本是每次实验 3.3 小时：$6\times1.27\times10^9\times5\times10^9=3.8\times10^{19}$ FLOPs，除以 $3.17\times10^{15}$。六次实验不到一天，占预算 4%。

短跑的结论有偏，要防一个陷阱：cosine 衰减的终点必须与 50 亿 token 匹配。如果沿用完整训练的衰减曲线只跑前 1.5%，比较的其实是"谁的退火更充分"，而不是谁的配方更好。同理，warmup 要按比例缩短，验证损失要取在每个实验自己的最后一步。

三道门槛过了，正式跑之前还有一件事：把恢复流程完整演练一次。杀进程、从最近的检查点重启、跑 100 步、比对 loss 与数据偏移是否与杀掉前一致。演练中发现的每一个问题，在 34 万步的训练里都会真实发生几十次。

### 跑起来之后：评测与检查点

正式跑开始后，团队的主要工作变成看数。看什么、多久看一次，直接决定了能不能在损失已经跑偏时及时刹车。

验证损失的采样频率可以算。验证集取 2000 万 token（与训练集去污染），一次评测需要 $2\times1.27\times10^9\times2\times10^7=5.1\times10^{16}$ FLOPs，在八卡上是 16 秒。每 1000 步（40 分钟）评一次，开销 0.7%，可以接受。

这份数字的可信度也要算。单个 token 的损失标准差大约 2.5 nat（下一个词的不确定性），2000 万 token 上均值的标准误是

$$\mathrm{SE}=\frac{2.5}{\sqrt{2\times10^7}}\approx5.6\times10^{-4}$$

白话：验证损失差 0.001 以内是噪声，不能当作"这个配方更好"的证据。想分辨 0.005 的差异，验证集得扩到百倍，或者看两条曲线在一万步尺度上的整体高低。

单看总损失不够，还要看分域损失：中文、英文、代码、数学各一份验证集，分别算。它们能直接回答配比问题——中文损失迟迟不降，说明中文占比或质量有问题；代码损失在训练中期先升后降是常态（模型先学自然语言再学代码的语法），早期看到它上升不必干预。

下游评测每 2 万步跑一次，选四个轻量任务：中文常识四选一、英文阅读理解、代码补全、数学应用题，各 2000 题。这个规模的采样噪声约 ±1.5 个点，只能看趋势，不能看单点。

最后一项最容易被省掉：生成抽检。固定 20 条 prompt（中英各半，包含续写、问答、代码、翻译），每 2 万步生成一次并存档。它是唯一能发现"损失降了但输出变差"的手段，而这种情况真的会发生——数据配比偏向短文本时，损失会降，但长文生成会退化成碎片。抽样的参数必须固定（温度 0.8、top-p 0.95、最大长度 256），否则两次抽检的差异里混着采样设置的差异，看不出模型的变化。

检查点按前面算过的最优间隔定：每 20 分钟一次（约 500 步），保留最近三个加每 2 万步的里程碑。13 亿参数的完整状态是 20GB，写到本地 SSD 只需几秒，异步写不阻塞训练。每 5 万步做一次恢复演练，不是可选项：检查点文件的损坏往往在需要它的那一刻才被发现。

日志里固定这几列：步数、损失、学习率、梯度范数的 99 分位、每层更新比、$\log Z$、注意力 logits 最大值、已见 token 数、各数据源的实际占比、吞吐（token/s）。前五项是稳定性那一章那套监控，后三项是配方自己的账——实际占比与设定配比不一致，通常意味着某个数据源读完了或者在重试。

### 出事时按什么顺序排查

训练跑起来之后的问题可以归成七类，每类的判据和第一步动作都是固定的。按这张表走，比每次从头想快得多。

| 现象 | 判据 | 先查什么 |
|---|---|---|
| 第一步损失远高于 10.4 | 第 1 步损失 >12 或 <8 | 输出层初始化、标签位移 |
| 损失长期平在 6–7 | 两万步降幅 <0.05 | 学习率与 warmup、数据是否重复 |
| 突然 NaN | 某步损失变成 nan | 学习率过大、缺 z-loss、fp16 溢出 |
| 验证损失先降后升 | 连续三次评测上升 | 数据重复 epoch 过多、验证集污染 |
| 训练损失降、生成变差 | 抽检发现重复与碎片 | 配比偏短文本、序列打包无边界重置 |
| 吞吐掉 20% 以上 | token/s 连续一小时低于基线 | 慢节点、网卡重传、数据 IO |
| 显存缓慢上涨 | 每小时涨 >1GB | 变长序列碎片、缓存未释放 |

第一类在门槛一就该被拦住。若漏到正式跑，最可能是输出层单独用了不同的初始化尺度（muP 下输出层是 $1/\text{fan\_in}$，与其他层不同），或者标签只移了位但没做掩码。

第二类是"能跑但学不动"。先看学习率是否被 warmup 压得太久（2000 步的 warmup 在 34 万步里只占 0.6%，如果误写成 2 万步就会明显拖慢）；再看数据是否在同一批上打转——数据加载器的随机种子若按 epoch 重置而 epoch 又设错，会出现每步都读同一段的情况，此时损失会降得很快然后卡住。

第三类 NaN 的定位靠二分:把学习率除以 3 重跑两千步,若不再 NaN,就是学习率问题;若仍 NaN，检查是否缺 z-loss（$\log Z$ 逐渐变负后 $e^{z}$ 下溢）或 QK-Norm（某个头 logits 超 88）。bf16 下 NaN 少见,一旦出现通常是真发散而不是溢出。

第四类要与"正常反弹"区分。验证损失在小批量下会抖，连续三次上升才是信号。真正的原因是重复 epoch 过多：数学数据设了 2.5 个 epoch，如果清洗时没去重、实际到了 5 个，模型在中后期就开始背答案。

第五类最隐：训练损失一直在降，但生成质量在退。判据是抽检里出现长段重复、句子变短、代码块不闭合。原因通常是配比里短文本（网页标题、短问答）占比过高，而打包时没在文档边界重置注意力，模型学会了跨文档接续。

第六类吞吐下降，九成是硬件或 IO。先看单卡利用率是否均等：某一张卡长期低于其他卡，就是慢节点，换掉即可（这也是前面说的热备卡的用处）。若全部卡一起掉，查数据管道——内存映射读本地盘时，页缓存被检查点写入冲掉会造成周期性卡顿，把检查点写到另一块盘上就解决了。

第七类显存缓慢上涨，通常是变长序列造成的碎片：每步的最大长度不同，缓存块分配器反复切分，碎片逐渐累积。修法是按长度分桶（同批内长度相近），或者在每个 epoch 结束时重启一次进程并恢复。

### 一张账单

把上面所有数字加起来，就是这次训练的真实成本。每一项都能从算力反推：

$$\text{GPU·小时}=\frac{6ND}{F_{\text{卡}}\times3600}$$

$F_{\text{卡}}$ 是单卡的有效算力，本配方里是 $990\times10^{12}\times0.4=3.96\times10^{14}$ FLOP/s。代入得 $2.65\times10^{21}/(1.43\times10^{18})=1860$ 卡·小时，这是零故障、满效率的理论值；乘上 0.85 的有效率就是 2690。后面每一项都用同一个式子估，再乘一个经验系数。

| 项 | GPU·小时 | 依据 |
|---|---|---|
| 正式训练 | 2690 | 9.4 天 × 8 卡 ÷ 0.85 有效率 |
| 配方短跑（6 次 × 5B token） | 160 | 每次 3.3 小时 |
| 恢复演练、评测与抽检 | 120 | 每 5 万步一次恢复演练，评测每千步一次 |
| 失败重跑与回滚 | 800 | 按 30% 余量估 |
| 数据清洗（分类器打分、嵌入去重） | 300 | 340B token 过一遍 5 亿参数分类器 |
| 合计 | 4070 | 约 500 卡·天 |

按每 GPU·小时 2 美元算，约 8000 美元。其中真正用于“学习”的只有 2690 小时，占 66%；剩下的全是验证、重跑和清洗。这个比例在小规模训练里是常态:模型越小,固定开销占比越高,所以小模型训练最该优化的往往不是模型本身,而是管道和流程。同样是这个金额,如果按租用算,刚好是八张卡两周的市价;如果自己买卡,一台八卡机约 25 万美元,摊到三年、每年跑十个这样的项目,单次成本相近--买卡换的是排队时间与数据不出门,不是单价。

存储另算：340B token 的 uint16 数组是 680GB，加 50 份检查点各 20GB 是 1TB，加实验期间的中间产物，预留 3TB 就够。网络不是瓶颈：八卡在同一个节点内，全部通信走 NVLink，连张量并行都不必开（$d=2048$ 时一层只有 5000 万参数，一张卡放得下），八张卡纯做数据并行加 ZeRO-1。这也是小模型训练与大规模训练最大的区别：后者一半的复杂度来自跨机通信，而这里根本没有跨机。

这份配方真正的价值不在那 4000 个 GPU·小时，而在它的可检验性。每一步都有判据,每个数字都能复算,每个失败模式都有对应的观察量。换一个规模,参数要重算,但顺序不变:先定预算与目标,再定词表与数据,再定模型与超参,然后过三道门槛,最后按表排查。

::: {.keypoint}
预训练不是把模型和数据的规模推大，而是把一堆可以互相校验的数字对齐：预算对得上算力，配比对得上损失，参数量对得上显存，检查点间隔对得上故障率。对不上的那一项，就是下一次事故的位置。
:::

一个 13 亿参数的模型，就这样从 680GB 的 token 数组里长出来。它能续写、能答简单问题、能补全代码，代价是两周和八千美元。但它读 2048 个 token 要用 197MB 的缓存（每 token 96KB：$2\times24\times8\times128\times2$ 字节），一张 80GB 的卡除去权重只能同时服务几百条序列；它每读一个 token 都要把全部 13 亿参数从显存里搬一遍，带宽决定了它每秒最多出几百个字。

这本账在推理侧是另一套算法，而降低这套算法的系数，靠的是改结构而不是改规模：把键值头再压一压、让注意力不要落地整块矩阵、把不同的 token 送给不同的专家、让位置编码支持更长的上下文。那些是第四卷的事——从这一个 token 的缓存开始。
