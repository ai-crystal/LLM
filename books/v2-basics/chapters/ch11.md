## 参数量、计算量与显存：一张账本

上一章把一个模型走到输出层，数清了每一步的形状。形状能告诉你“要乘多少次”，但回答不了三个更要紧的问题：一张 80GB 的卡能不能装下一个 70B 模型；把它训练出来要多少张卡跑多少天；服务一个用户，每一千个 token 要花多少电。

这三个问题的答案写在同一个地方：一张账本。账本上有三个量——参数量 $N$、训练 token 数 $D$、上下文长度 $T$。$N$ 决定显存和权重的读取量，$6ND$ 决定训练的总算力，$2N$ 决定推理每步的算力，而 $2Lh_{kv}d_{\text{head}}T$ 决定每个请求占多少缓存。这一章不做别的，就把这几行账一行行推出来，再用真实的模型对一遍。

### 参数住在哪里

先数参数。一个 Transformer 层有两块：注意力与前馈。

注意力的四个投影都是 $d\times d$：$W^Q$、$W^K$、$W^V$、$W^O$。四个矩阵各 $d^2$ 个权重，合计 $4d^2$。这里假设 $d_k=d_v=d$，也就是每个头的维度乘以头数正好等于模型维度——绝大多数模型都这么设，省得再引入一个超参。

前馈是两个矩阵：先把 $d$ 升到 $d_{ff}$，再降回 $d$。$d_{ff}$ 通常取 $4d$，于是两个矩阵是 $d\times4d$ 和 $4d\times d$，各 $4d^2$，合计 $8d^2$。

两个 LayerNorm 各有 $2d$ 个可学参数（缩放 $\gamma$ 和偏移 $\beta$），合计 $4d$。这一项在 $d=4096$ 时是 16384，与 $4d^2=1677$ 万相比可以忽略，但它在推理时要读一遍，算带宽账时不能完全当零。

一层合计：

$$4d^2+8d^2+4d=12d^2+4d$$

$L$ 层就是 $L(12d^2+4d)$。再加上词嵌入表 $V\times d$：$V$ 是词表大小。如果输出层不与嵌入共享权重，还要再来一个 $V\times d$。

$$N\approx 12Ld^2+Vd$$

这个式子的用法是反查。拿到一个模型的配置，量一下 $d$ 和 $L$，乘一下就知道量级；反过来，给定预算，也能估出能训多大的模型。$d=4096$、$L=32$ 时，$12Ld^2=12\times32\times1.68\times10^7=6.44\times10^9$，加上词表 $32000\times4096=1.31\times10^8$，得到 65.7 亿。这就是“7B 级”这个说法的来历。

拆到一层看更清楚。$d=4096$ 时 $d^2=1677$ 万，四个投影各这么多，注意力 6710 万；前馈两个矩阵各 $d\times4d$，共 1.34 亿；一层 2.01 亿。32 层是 64.4 亿，再加词表。每一层的数字完全一样，所以参数量对层数是严格线性的，对宽度是严格平方的：宽度翻倍，参数翻四倍；层数翻倍，参数翻两倍。这两个指数决定了所有容量规划的形状。

这个公式还有一个容易被忽略的性质：它对 $d$ 的依赖只有平方，不区分哪一维是“头”，哪一维是“隐藏”。把 $d$ 拆成 32 个头、每头 128 维，算出来的参数和“一个 4096 维的大头”完全一样。多头不是靠增加参数换性能的，它换的是并行的粒度和表达的分工。

词表那一项常常被忽略，但它不该被忽略。$Vd$ 与 $12Ld^2$ 的比值是 $V/(12Ld)$：7B 配置下是 $32000/(12\times32\times4096)=2\%$，确实小；可一个 1B 的模型若用 25 万词表（多语言模型常见），比值就爬到 30% 以上，参数里近三分之一住在一张查表矩阵里。这也解释了为什么小模型的多语言能力往往不如大模型：词表撑大了，真正用于计算的层就薄了。

前馈占的比例也值得记一笔：每层十二份参数里，八份在前馈。注意力只在位置之间搬运，前馈在位置上做变换，参数的大头给了后者。后面讲混合专家时，切的就是这块最肥的肉。

### 换结构，账要重算

上面的 12 是个平均数，换个结构就不是它了。两处最常见的改动，恰好一处减参数、一处加参数。

**分组查询注意力（Grouped Query Attention，GQA）** 改的是 $K$、$V$ 的宽度。标准多头里，$W^K$ 和 $W^V$ 各是 $d\times d$；GQA 让若干个查询头共享一组键值头，键值头数 $h_{kv}$ 小于查询头数 $h$，每个键值头仍然是 $d_{\text{head}}$ 维，于是

$$W^K,W^V\in\mathbb{R}^{d\times h_{kv}d_{\text{head}}}$$

参数从 $2d^2$ 降到 $2d\,h_{kv}d_{\text{head}}$。Llama-2 70B 取 $h=64$、$h_{kv}=8$、$d_{\text{head}}=128$，$h_{kv}d_{\text{head}}=1024$，比 $d=8192$ 小 8 倍：键值投影从每个 $6.7\times10^7$ 个权重降到 $8.4\times10^6$，一层省下 1.17 亿，80 层省下 94 亿。这不是小数，占了 70B 全部参数的 13%。

**门控线性单元（Gated Linear Unit，GLU）** 改的是前馈。原来的两个矩阵变成三个：一个做门控，一个做内容，逐元素相乘后再降维。三个矩阵若都保持 $d_{ff}=4d$，参数变成 $12d^2$，凭空多出五成。所以采用 GLU 的模型会把宽度压到 $\frac{2}{3}\times4d=\frac{8d}{3}$，此时 $3\times d\times\frac{8d}{3}=8d^2$，与前馈的原账持平。Llama 系列没有严格照做，它取 $d_{ff}=3.5d$，比持平配置多三成参数，换来更低的损失。

把两处改动都算进去，再对一遍 70B 的账：

| 项 | 算式 | 每层 |
|---|---|---|
| $W^Q$ | $d^2$ | 67.1M |
| $W^K$、$W^V$ | $2\times d\times h_{kv}d_{\text{head}}$ | 16.8M |
| $W^O$ | $d^2$ | 67.1M |
| 前馈（SwiGLU） | $3\times d\times 3.5d$ | 704.6M |
| 两个归一化 | $4d$ | 0.03M |
| 合计 | | 855.6M |

乘 80 层是 684.5 亿，加上两份词表（$32000\times8192\times2=5.2$ 亿），得到 689.7 亿。Llama-2 70B 官方报的数是 689.8 亿，误差在千分之一以内。这比对上了不是巧合：它说明“参数都住在哪里”这件事已经被拆干净了，没有藏着的项。

用 12d²L 直接套这个模型会得到 644 亿，少了 46 亿。少的这 46 亿是两笔相反的账相抵的结果：SwiGLU 多出一个矩阵（$+2.5d^2$ 每层），GQA 砍掉大部分键值投影（$-1.75d^2$ 每层），净增 $0.75d^2\times80=40$ 亿，再加上共享与否的词表差。**$12d^2$ 是骨架的公式，不是任何具体模型的公式。** 遇到新结构，回到那张分层表重算一遍，比套公式可靠。

用同样的方法对一遍 7B：$d=4096$、$L=32$、$h=32$、$d_{\text{head}}=128$，用满多头，所以键值投影不缩，$4d^2=6710$ 万；前馈取 $d_{ff}=11008$（2.69 倍），三个矩阵共 $3\times4096\times11008=1.353$ 亿；一层 2.02 亿，32 层 64.8 亿。词表如果在输入和输出两侧各有一份，加上 $2\times1.31$ 亿，得 67.4 亿，正好是官方报的 6.74B。两份词表这件事在配置里就写着（`tie_word_embeddings: false`），只是很少有人去数它。

### 训练一次要多少浮点运算

前向的算力可以精确地数。一个参数参与运算，一定是一次乘法加一次加法，计 2 次浮点运算（FLOPs）。一层矩阵乘法 $[T,d]\times[d,d']$ 需要 $2Tdd'$ 次浮点运算，这个 2 就是乘加各算一次。如果序列有 $T$ 个 token，而这 $T$ 个 token 全部流过同一个参数矩阵，那么每个参数被用了 $T$ 次，于是

$$\text{前向}=2N\quad(\text{每个 token})$$

这里的 $N$ 是全部参数。注意它不区分注意力还是前馈：只要参数在计算路径上，就被用一次。唯一例外是注意力里的 $T^2$ 项，它不含参数，只含位置对，后面单独算。

反向传播的账要多一倍。对每个权重 $w$，反向要算两件事：损失对 $w$ 的梯度（用上游梯度乘以前向的输入），和损失对输入的梯度（用上游梯度乘以 $w$，再传给下一层）。两件事各是一次乘加，各 2 次运算，所以每个参数 4 次：

$$\text{反向}=4N\quad(\text{每个 token})$$

写成矩阵更清楚。一层的前向是 $Y=XW$，$X$ 是 $T\times d$，$W$ 是 $d\times d'$。反向收到 $\partial\mathcal{L}/\partial Y$（同样 $T\times d'$），要算两个东西：

$$\frac{\partial\mathcal{L}}{\partial W}=X^{\top}\frac{\partial\mathcal{L}}{\partial Y},\qquad \frac{\partial\mathcal{L}}{\partial X}=\frac{\partial\mathcal{L}}{\partial Y}W^{\top}$$

第一个是 $[d,T]\times[T,d']$，需 $2Tdd'$；第二个是 $[T,d']\times[d',d]$，也是 $2Tdd'$。两者相加 $4Tdd'$，而前向只用了 $2Tdd'$。这正是“反向是前向两倍”的来源：多出来的那一倍不是为了算梯度下降，是为了把梯度继续往前传。没有第二项，只有最后一层能更新，前面所有层都收不到信号。

合起来，每个 token 训练一次要 $6N$ 次浮点运算。训练 $D$ 个 token：

$$\text{训练总算力}\approx 6ND$$

这个式子是整个行业最常用的估算。它没有考虑注意力的 $T^2$ 项，也没有考虑激活函数、归一化、softmax 这些非矩阵运算的部分——后者约占 5% 到 10%，对量级没有影响。

```text
每 token 前向：2 × N 次乘加
每 token 反向：4 × N（2N 算权重梯度 + 2N 算输入梯度）
每 token 合计：6N
训练总量：6 × N × D
```

拿 7B 模型训 2 万亿 token 试一下：$6\times6.74\times10^9\times2\times10^{12}=8.1\times10^{22}$ 次浮点运算。这个数没有直觉，换成硬件时间：一张 A100 的 bf16 峰值是 312 TFLOPS，也就是每秒 $3.12\times10^{14}$ 次。理论上需要 $2.6\times10^8$ 秒，一张卡跑八年。用一千张卡，理论上三天；实际达不到峰值，按 40% 的利用率算，七天半。

$D$ 取多少不是自由选择。它由“每个参数分到多少 token”决定，也就是 $D/N$ 这个比值——缩放定律那一卷会详细展开，这里只记结论：最早的一批模型取 1 到 2（GPT-3 是 3000 亿 token 对 1750 亿参数，约 1.7）；2022 年之后，按“算力最优”重新算过的配方把这个比值推到 20；再往后，因为推理成本比训练成本更贵，开源模型普遍取到 200 以上（Llama-2 7B 是 2 万亿对 67 亿，约 300）。比值越大，$6ND$ 里 $D$ 的那一项越重，同样的参数就要更多的算力。这就是为什么“同样一个 7B，有人花 10 万美元训完，有人花 100 万”：差别不在模型，在喂了多少 token。

“实际达不到峰值”这件事有个名字：模型算力利用率（Model FLOPs Utilization，MFU），就是实际吞吐除以硬件峰值。大模型训练里 35% 到 50% 是常见区间，剩下的算力耗在通信、等待、显存读写上。反过来，知道 MFU 就能从公开的 GPU 小时数反推算力需求。《Llama 2》那份报告给了两个数：7B 用了 184,320 GPU 小时，70B 用了 1,720,320 GPU 小时（都是 A100 80GB）。用 $6ND$ 反推，7B 的等效算力是 $8.1\times10^{22}/(184320\times3600)=1.22\times10^{14}$，MFU 39%；70B 训 2 万亿 token 需要 $8.28\times10^{23}$，等效 $1.34\times10^{14}$，MFU 43%。两个数都落在常识区间里，说明这套估算法可信。

账算到这里还只是一半。$6ND$ 说的是“算多久”，还有“装不装得下”。一个 7B 模型用 Adam 混合精度训练，每个参数要占：bf16 权重 2 字节、bf16 梯度 2 字节、fp32 主权重 4 字节、一阶动量 4 字节、二阶动量 4 字节，合计 16 字节。$6.74\times10^9\times16=108$ GB，一张 80GB 的卡连状态都放不下，更不用说激活值。所以哪怕只训 7B，也必须切分：数据并行把 batch 摊开，ZeRO 把优化器状态分片，张量并行把单层切开。这些手段的细节属于预训练系统的话题，这里只记一个结论：**训练时的显存需求不是 $2N$ 字节，而是 $16N$ 字节，差八倍。**

::: {.keypoint}
参数量 $N$ 决定权重占多少显存（推理 $2N$ 字节，训练 $16N$ 字节）；$6ND$ 决定训练要多少算力；$2N$ 决定推理每个 token 的算力；$2Lh_{kv}d_{\text{head}}T$ 决定每个并发请求占多少缓存。四笔账，四个不同的瓶颈。
:::

### 推理：每个 token 两倍的 N

推理没有反向，每个 token 只要前向的 $2N$：

$$\text{推理}=2N\quad(\text{每个新 token})$$

70B 模型生成一个 token 要 $2\times6.9\times10^{10}=1.38\times10^{11}$ 次浮点运算。一千个 token 是 $1.4\times10^{14}$，看起来不多——一张 A100 按峰值算半秒就能算完。可实际上生成一千个 token 要十几秒，差距在两个数量级。

原因在注意力与“两段式”。一次请求分两段。预填充（prefill）把用户输入的 $T$ 个 token 一次性送进去，所有位置并行，算力是 $2NT$，$T$ 越大这一段越久，但摊到每个 token 上很便宜。解码（decode）每次只处理一个新 token，它要读全部权重，却只做 $2N$ 次运算。同一份权重，预填充时被 $T$ 个 token 共用，解码时只被一个 token 用。

这就是问题的根：解码的算术强度极低。每个权重被读进计算单元，只参与两次运算就被丢掉了。计算单元大部分时间在等数据从显存搬过来。瓶颈不在算力，在带宽。

两段的差距可以用一组数字钉住。7B 模型处理 4K 输入的预填充，算力是 $2NT=2\times6.74\times10^9\times4096=5.5\times10^{13}$，一张 A100 按 40% 利用率算是 0.44 秒——这就是用户感知到的“首字延迟”。同一模型解码一个 token 要 $1.35\times10^{10}$ 次运算，按算力算只占 0.1 毫秒，实际却要 7 到 10 毫秒，差的那两个数量级全是等权重的时间。

所以“推理算力是 $2N$”这句话只说对了一半。它对容量规划有用：一天服务多少 token，乘上 $2N$ 就是总算力。但它预测不了延迟，延迟由带宽和缓存决定，而缓存是 $2N$ 里没有的项。这两件事分开算，才不会把“卡不够快”误判成“算力不够”。

### KV 缓存：一条随对话变长的账

解码时唯一被复用的是历史的键和值。第 $t$ 个位置在每一层都要留下自己算好的 $k$ 和 $v$，供后面的位置查询。这些张量的总量是

$$\text{KV 缓存}=2\times L\times h_{kv}\times d_{\text{head}}\times T\times b$$

系数 2 是键和值两份；$L$ 是层数，每层各存一份；$h_{kv}d_{\text{head}}$ 是每层键（或值）的宽度，$T$ 是已缓存的 token 数，$b$ 是每个数占的字节数（FP16 是 2）。$T$ 是变量，其余都是模型的常数。把常数部分打包，得到“每 token 每层多少字节”，这是估容量时最常用的一个数。

7B 模型（$L=32$、$h_{kv}=32$、$d_{\text{head}}=128$、FP16）每 token 是 $2\times32\times32\times128\times2=524288$ 字节，正好 0.5MB。四千 token 的对话占 2.1GB——比模型权重（13.5GB）小，但它是每个请求一份，不能共享。八个并发就是 17GB，卡上就没剩多少了。

70B 用 GQA，$h_{kv}d_{\text{head}}=1024$，每 token 是 $2\times80\times1024\times2=327680$ 字节，0.32MB。同样的四千 token 只要 1.3GB。如果这个模型用满 64 个键值头，每 token 会变成 2.6MB，四千 token 就是 10.7GB，八倍。**GQA 把缓存砍到八分之一，这一刀砍的是并发数**：同样的显存，能同时服务八倍的请求。

上下文拉长，这笔账变得很难看。128K token 的对话，70B 的缓存是 $327680\times131072=4.3\times10^{10}$ 字节，43GB。一张 80GB 的卡切走 17GB 放权重，剩下 63GB，只够放 1.4 个这样的请求。也就是说，128K 上下文下，一张卡基本只能服务一个长对话。7B 模型若用满多头，128K 要 68GB，一张卡连一个都放不下。

还有一条不那么显眼的分界线。解码每步要读两样东西：权重和缓存。权重是常数（70B 约 138GB），缓存随 $T$ 线性长。两者相等的位置在

$$T^{*}=\frac{2N}{2Lh_{kv}d_{\text{head}}b}$$

70B 代入得 $1.38\times10^{11}/327680\approx4.2\times10^{5}$，四十二万 token。超过这个长度，解码的主要带宽开销就不再是权重，而是缓存。今天的长上下文还停在二十万到一百万之间，正好压在这条线上——这也是为什么长上下文的成本曲线在十万 token 之后突然变陡。

缓存管理因此成了独立的工程问题。最直接的做法是按最大长度预分配：一个声明支持 32K 的请求，一进来就占 32K 的缓存，不管它实际聊了多长。结果是显存被大量空页占着，并发上不去。分页缓存（PagedAttention）把缓存切成固定大小的块，按需分配，聊到哪分到哪，块之间不要求连续，靠一张表把逻辑位置映射到物理块。它把显存浪费从“平均用不到一半”压到“最后一个块用不完”。

另一条路是共享。同一个系统提示、同一段长文档、同一批并行采样，前缀完全一样，对应的键值也完全一样，没有理由存很多份。把前缀的物理块引用计数共享出去，十个请求读同一篇文档，缓存只存一份，显存需求降到十分之一。这条优化对检索类应用特别有效，因为它们的提示里大半是重复的文档。

再往下就是改结构了。多查询注意力（Multi-Query Attention，MQA）把所有查询头压到共享一组键值，$h_{kv}=1$，缓存降到 $1/h$，代价是表达力下降、训练不稳。GQA 取中间值，八个查询头共享一组键值。多头潜在注意力（Multi-head Latent Attention，MLA）换了个思路：不存键和值本身，存一个低秩的压缩向量，用的时候再投影回去，缓存能再降一个数量级。三条路改的都是同一行公式里的 $h_{kv}d_{\text{head}}$，而这一行决定了并发数。

### 带宽：真正的墙

把“算力”和“带宽”放在一张图上，就是所谓的屋顶线（roofline）。横轴是算术强度，即每搬一个字节能做多少次运算；纵轴是实际能达到的算力。强度低的时候，性能被带宽卡住，斜率就是带宽；强度高的时候，被峰值算力卡住，曲线变平。两条线的交点叫拐点：

$$\text{拐点}=\frac{\text{峰值算力}}{\text{带宽}}$$

A100 是 $3.12\times10^{14}/2.04\times10^{12}=153$ FLOPs/字节，H100 是 $9.9\times10^{14}/3.35\times10^{12}=295$。

这两个数不是天生如此。带宽是显存颗粒每秒能吐多少字节，由内存接口的位宽和频率决定；算力是计算单元每秒能做多少次乘加，由芯片面积和制程决定。两条线跑得不一样快：K80 的 8.7 TFLOPS 配 480GB/s，拐点在 18；H100 的 990 TFLOPS 配 3.35TB/s，拐点 295。算力涨了两个数量级，带宽只涨了七倍，于是拐点从左向右一路滑。十年前，一个人不难写出一段卡在算力区的代码；现在，任何带宽复用不够的算法都会自动掉进带宽区。深度学习的大部分算子形状都是“读一大批数据，做很少运算”，这个滑移对它们不是好消息。

解码的算术强度是多少？一个 batch 里 $B$ 个请求，各自带着自己的缓存，共用同一份权重。每步运算 $2NB$，搬动权重 $2N$ 字节，所以

$$	ext{强度}\approx B\quad(	ext{FLOPs/字节})$$

（这里只算权重；缓存的开销后面单独算，它会把强度再拉低。）

批大小为 1 时，强度是 1，与拐点 153 差了 150 倍。这意味着单请求解码只用到峰值算力的 0.7%。把批大小抬到 150，强度才追平拐点；再往上加，才开始受算力限制。

同一条推导能解释三个现象。

一是为什么解码速度有一个硬上限。单请求时，每秒能生成多少 token 等于带宽除以权重字节数：

$$\text{tokens/s}\le\frac{\text{带宽}}{2N}$$

7B 在 A100 上是 $2.04\times10^{12}/1.35\times10^{10}=151$，实测单流大约 100，差距来自缓存读取、内核启动、采样这些开销。70B 用八张 A100 做张量并行，合计带宽 16.3TB/s，理论上限 118 token/s，实测通常 30 到 50——差的那部分是卡间通信，每层两次全归约，一次也省不掉。

二是为什么批处理是推理服务的第一性优化。批大小从 1 抬到 32，吞吐接近线性涨，因为同一份权重被 32 个请求共用；延迟几乎不变，因为瓶颈仍是读权重那一次。这就是连续批处理（continuous batching）值钱的地方。但它有上限：强度到 153 之后，算力成了新瓶颈，再加批只会一起变慢。

把这个上限算成数字。70B 模型在八张 A100 上，每吐一个 token 要做 $1.38\times10^{11}$ 次运算，八卡合计算力 $2.5\times10^{15}$，纯算力允许一万八千 token/s；带宽那一侧的 118 除以它，就是拐点 153 的具体形态：要么把批堆到 150，要么认下这 150 倍的浪费。而一个 128K 的请求就要占 43GB 缓存，堆 150 个需要六千多 GB，物理上不可能。所以长上下文和高吞吐从来不能同时要。

三是为什么量化对解码特别有效。权重从 FP16 压到 INT8，字节数减半，同样带宽下解码速度接近翻倍，而精度损失通常很小。这不是因为整数运算更快，是因为要搬的东西少了一半。7B 模型 FP16 是 13.5GB，A100 上的理论上限 151 token/s；换成 INT8 是 6.7GB，上限变成 304；再压到 INT4 是 3.4GB，上限 608。这条换算关系比任何基准测试都直接：解码速度大致与权重字节数成反比。同一套道理也解释了为什么 MoE 在推理侧有吸引力：激活的参数少，要读的权重就少——但那是另一卷的话题。

预填充则完全相反。$T$ 个 token 共用一次权重读取，强度约为 $T$，128K 上下文下是十几万，远超拐点，纯粹受算力限制。所以同一个模型，预填充是算力问题，解码是带宽问题，优化手段完全不同：前者要更快的矩阵乘和更好的并行，后者要更大的带宽、更小的权重、更高的批。

### 两个 N：稠密与稀疏

上面所有的账都假定“每个参数在每个 token 上都被用到”。混合专家（Mixture of Experts，MoE）打破了这个前提：一层里的前馈被拆成 $E$ 个专家，每个 token 只被路由到其中 $k$ 个。于是出现两个不同的 $N$。

总参数 $N_{\text{total}}$ 是全部专家的和，决定权重占多少显存；激活参数 $N_{\text{active}}$ 是每个 token 真正走过的部分，决定算力和带宽。一个 8×22B 的模型，总参数 1410 亿，激活 390 亿：每层八个专家，每个 token 选两个。

两笔账分开算。显存按 $N_{\text{total}}$：FP16 下 282GB，至少要四张 80GB 的卡才装得下。算力按 $N_{\text{active}}$：$2\times3.9\times10^{10}=7.8\times10^{10}$ 每 token，比稠密 70B 的 $1.38\times10^{11}$ 还少四成，而它的总参数是 70B 的两倍。解码时读的也是激活的那部分权重，所以出字速度接近一个 39B 的稠密模型。

KV 缓存是第三本账，它只跟层数和键值头有关，跟专家数量无关：一个 8×22B 的模型，若 $L=56$、$h_{kv}d_{\text{head}}=1024$，每 token 是 $2\times56\times1024\times2=229$ KB，比稠密 70B 的 320KB 还小。MoE 在这个账本上有两处便宜、一处贵：算力便宜、带宽便宜、显存贵。

这个区分之所以重要，是因为很多论文里的 $N$ 不加限定。缩放定律里的 $N$ 通常指总参数（它要和 $D$ 一起决定损失），而 $6ND$ 里的 $N$ 必须是激活参数（它决定真实算了多少次）。拿总参数去乘 $6D$，会把训练算力估高两到三倍；反过来，拿激活参数去算显存，会以为一张卡能装下一个装不下的模型。看到任何参数量，先问一句是哪个 N，比记住任何公式都有用。

### 为什么长上下文贵

把前面几笔账合起来，长上下文的成本来自三个互相独立的地方，而它们增长的速度不一样。

第一处是注意力的计算量。每层注意力的打分与加权各是一次 $T\times T$ 的矩阵乘，合计 $4T^2d$ 次运算；而每层的线性部分（投影与前馈）是 $24Td^2$。两者相等的位置在

$$4T^2d=24Td^2\quad\Longrightarrow\quad T^{*}=6d$$

$d=8192$ 时，拐点在四万九千 token。短于它，模型的时间花在矩阵乘权重上；长于它，时间花在位置两两打分上，而且按平方涨。这就是为什么 4K 上下文的模型和 128K 上下文的模型，优化重点完全不同：前者几乎感觉不到注意力，后者一半以上的算力在注意力里。

具体量一下。70B 模型处理 128K 的输入，线性部分是 $2NT=2\times6.9\times10^{10}\times1.31\times10^5=1.8\times10^{16}$，注意力部分是 $4\times80\times8192\times(1.31\times10^5)^2=4.5\times10^{16}$，合计 $6.3\times10^{16}$，六十三拍浮点运算。八张 A100 按 40% 利用率跑，要六十多秒。同样的模型处理 8K 输入，总量是 $1.3\times10^{15}$，一秒出头。长度涨 16 倍，算力涨 48 倍——多出来的那三倍，全是平方项。

第二处是缓存占的显存，前面算过，43GB。它不参与计算，只是占着地方，把并发数压到 1。

第三处是解码时每步要读的缓存。128K 时每步读 43GB 缓存加 138GB 权重，合计 181GB；八卡合计带宽 16.3TB/s，理论上限降到 90 token/s，再打上通信和调度的折扣，实际可能只有二三十。上下文从 8K 涨到 128K，单请求解码速度掉了三到四倍，而用户对“出字速度”的感知非常直接。

三条线不在同一个长度上转折。按算力算，$T^{*}=6d$，$d=8192$ 时是四万九千；按显存算，缓存从第一个 token 就开始线性涨，没有拐点；按带宽算，拐点在四十二万。三十二 K 的上下文刚好落在算力拐点之前——注意力只占三成，成本还算温和；一百二十八 K 已经远远超出，注意力是线性部分的两倍半。这解释了一个现象：同样叫“长上下文”，32K 和 128K 在工程上是两个不同的物种，不是一个调大参数就能跨过去的。

三处叠起来，长上下文的价格不是线性涨的，而是“算力按平方、显存按线性、速度按线性”三重叠加。工程上的应对各自针对一处：FlashAttention 与稀疏注意力打第一处，GQA 与 MLA 打第二处，分页缓存与前缀复用打第三处。它们的共同点是都在改这本账的某一行，而不是在改模型的能力。

这本账到这里就记完了。回头看，第一卷说“一次生成是几百次同样的计算首尾相接”，这一卷把“同样的计算”拆成了具体的矩阵、具体的形状、具体的字节数。$12Ld^2$ 告诉你参数住在哪里，$6ND$ 告诉你训练的代价，$2N$ 与 $2Lh_{kv}d_{\text{head}}T$ 告诉你服务的边界。这些式子不会因为模型变大而失效，只会因为结构变化而需要重算——前面 70B 那笔账就是例子。

账本的下一页在预训练。权重不是凭空来的：要多少 token 才够，数据从哪里来、怎么洗、怎么配比，词表定多大，规模上去之后损失按什么规律下降。这些问题决定 $N$ 和 $D$ 该取多少，而这一章给了它们一把尺子——任何一个配方，最后都要落回这三行数字上，看它在算力、显存、带宽之间换到了什么。
